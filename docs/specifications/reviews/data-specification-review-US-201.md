# Data Specification Review (US-201)

## 結論
- 承認（現時点要件に対して過不足なし）。

## 懸念点
1. `VARCHAR(500)` は将来の絵文字等で「体感文字数」との差異が起きうる。
2. notes 検索要件が将来追加された場合、現設計では即時に検索効率を担保できない。

## 代替案と却下理由
1. **代替案**: Notes 専用テーブル（`website_note`）を追加。  
   **却下理由**: 現要件は単一最新値の保持のみで、Join 増加は過剰設計。
2. **代替案**: `TEXT` 型を採用しアプリ側のみ 500 文字制限。  
   **却下理由**: DB 制約が弱くなり、アプリバグ時に上限超過データが混入しうるため。
3. **代替案**: `NOT NULL DEFAULT ''`。  
   **却下理由**: 「未設定」と「空文字」の意味境界が曖昧になり、表示判定が複雑化するため。

## 採用時のガード
1. nullable + 長さ制約で後方互換を保ちながら不正データ混入を抑制。
2. 空文字はアプリ層で `NULL` 正規化してデータ一貫性を維持。
