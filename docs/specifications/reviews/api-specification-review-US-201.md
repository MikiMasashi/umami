## 2. 主要な設計判断と根拠

### 2.1 note フィールドをオプション（POST body）とした理由

**判断**: POST /api/websites/{websiteId} で note を optional フィールドとする

**理由**:
1. 既存の name・domain・shareId と同じパターン（partial update）
2. クライアント側での必須入力ではない（メモ編集後に保存する操作のみ対象）
3. 既存システムの partial update パターンと一貫性あり

**代替案と却下理由**:
- **案A**: note を required フィールドとする
  - 却下理由: 既存の API パターンと異なる（name も required ではない）

---

### 2.2 バリデーションエラーメッセージの表現

**判断**: "Note must be 500 characters or less" を採用

**根拠**:
1. umami の既存エラーメッセージスタイルに一致
2. 英語での統一（umami は英語ベースで i18n）
3. 明確で行動可能な表現（何が問題で、どう対応するか明白）

**代替案と却下理由**:
- **案A**: "500文字以内で入力してください" (日本語固定)
  - 却下理由: i18n 対応が必要（umami の多言語対応方針と不一致）

- **案B**: "Validation error: note length" (技術的表現)
  - 却下理由: ユーザーに意図が不明確

---

### 2.3 note を GET レスポンスに常に含める

**判断**: GET /api/websites/{websiteId} でも GET /api/websites でも note を返却

**根拠**:
1. Prisma の自動フィールド取得（指定しなくても全フィールド返却）
2. クライアント側で note を無視する選択が可能（後方互換性）
3. 明示的な select を指定しない限り、Prisma は全フィールド返却

**代替案と却下理由**:
- **案A**: GET ではデフォルト note を返さず、必要時のみ select で取得
  - 却下理由: Prisma の標準動作に逆らう。クエリを複雑にする。メリットなし。

## 3. 懸念点の分析と対応

### 3.1 懸念点1: 文字数制約の多重実装

**懸念**: DB レイヤー（VARCHAR(500)）と API レイヤー（zod）で同じ制約を実装

**リスク**: 制約値が不一致になる可能性

**対応方法**:
1. **制約値の一元管理**: `src/lib/constants.ts` で定義
   ```typescript
   export const WEBSITE_NOTE_MAX_LENGTH = 500;
   ```
2. **スキーマ共有**: zod と Prisma で同じ定数を使用
   ```typescript
   // zod: note: z.string().max(WEBSITE_NOTE_MAX_LENGTH)
   // Prisma: note String? @db.VarChar(WEBSITE_NOTE_MAX_LENGTH)
   ```
3. **テスト**: 境界値テスト（499、500、501 文字）で制約を検証

**リスク度**: 低（定数管理で対応可能）

---

### 3.2 懸念点2: エラーメッセージの多言語対応

**懸念**: "Note must be 500 characters or less" が固定値

**リスク**: 多言語非対応のユーザーが理解できない

**対応方法**:
1. **i18n キーの定義**: umami の i18n システムを使用
   ```typescript
   const messages = useMessages();
   const errorMsg = t(messages.noteMustBe500CharsOrLess);
   ```
2. **翻訳ファイル更新**: `src/i18n/locales/` に各言語の翻訳を追加
3. **バリデーション時の i18n 対応**:
   ```typescript
   note: z.string()
     .max(500, t(messages.noteMustBe500CharsOrLess))
   ```

**リスク度**: 中（実装時に i18n 機構と統合する必要あり。ただし手順は明確）

**実装責任**: Backend Engineer（i18n ファイル更新）+ Frontend Engineer（メッセージ表示）

---

### 3.3 懸念点3: GET /api/websites での検索対象に note が含まれていない

**懸念**: メモ検索機能が将来追加されるときの拡張性

**リスク**: 現在の実装では検索対象が name・domain のみ。将来的に note を検索対象にしたい場合、設計変更が必要

**対応方法**:
1. **現在の決定**: note は検索対象外（要件スコープ外）
2. **将来の拡張**: メモ検索機能が必要になった際に以下を検討
   - DB インデックス: FULLTEXT INDEX or GIN インデックス
   - クエリ修正: getWebsites() の WHERE 句に note を追加
   - API 設計: 検索パラメータの拡張（`searchFields` など）

**リスク度**: 低（将来検討との明確な切り分け。現在は影響なし）

---

### 3.4 懸念点4: 空文字列と null の扱い

**懸念**: クライアントが空文字列を送信した場合の動作

**現在の設計**: API Route Handler で `"" → null` に正規化

```typescript
const updateData = { ...body };
if (body.note === "") {
  updateData.note = null;
}
const website = await updateWebsite(websiteId, updateData);
```

**リスク**: クライアント側で空文字列を送信するケースが多い場合、サーバー側でいちいち正規化する手間

**対応方法**:
1. **クライアント側での事前処理**: WebsiteEditForm で空文字列を null に変換してから API 呼び出し
   ```typescript
   const data = { note: note === "" ? null : note };
   await mutateAsync(data);
   ```
2. **サーバー側での保険的処理**: 上記の正規化コードをキープ（防御的プログラミング）

**リスク度**: 低（クライアント・サーバーの双方で対応可能。既存パターン）

## 4. 設計判断のトレードオフ

### 4.1 REST API vs GraphQL

**検討対象**: メモ機能に GraphQL を採用するべきか？

**決定**: REST API を採用（umami 既存パターンに従う）

**トレードオフ分析**:

| 項目 | REST | GraphQL |
|---|---|---|
| 学習曲線 | 低 | 中（schema 定義・resolver 実装） |
| 開発速度 | 速い | やや遅い（初期設定コスト） |
| 実装複雑度 | 低 | 中 |
| メモ機能のような単純な CRUD に対する適性 | 高 | 過剰設計 |
| 既存システムとの整合性 | ✅ umami は REST API ベース | ✅ 移行が必要 |

**結論**: REST API を採用。GraphQL への移行コストが大きく、メリット不明確。

---

### 4.2 VARCHAR(500) vs TEXT

**検討対象**: データベース型の選択

**決定**: VARCHAR(500) を採用

**トレードオフ分析**:

| 項目 | VARCHAR(500) | TEXT |
|---|---|---|
| 格納効率 | 高（実サイズ） | 低（固定オーバーヘッド） |
| 文字数制限の強制 | ✅ DB が強制 | ❌ アプリが強制 |
| インデックス対応 | 容易 | 困難（FULLTEXT only） |
| スケーラビリティ | ✅ 500文字制限あり | 無制限（将来の課題） |

**結論**: VARCHAR(500)。要件で上限 500 文字と明示されており、DB 側で制約を強制できる利点あり。

## 5. パフォーマンス検証

### 5.1 クエリパフォーマンス

**テスト想定**:

```sql
-- Website テーブル: 100,000 レコード
-- note フィールド: VARCHAR(500)、平均 100 文字（日本語 300 バイト）

-- クエリ実行計画（Explain）
EXPLAIN ANALYZE
SELECT id, name, domain, note, createdAt
FROM website
WHERE user_id = $1 AND deleted_at IS NULL
ORDER BY name ASC
LIMIT 20;
```

**予想結果**: Index Scan (user_id, deleted_at, name) で十分

**note 追加による性能低下**: 無視可能（SELECT の対象フィールド追加のみ）

### 5.2 ネットワークスループット

**API レスポンスサイズの増加**:

```

- 1 サイト当たり: ~300 bytes

変更後（note フィールド追加）:
- 1 サイト当たり: ~400 bytes（note 平均 100 文字）

増加分: 2 KB（ネットワークに無視可能な影響）
```
