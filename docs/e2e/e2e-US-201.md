# E2E テスト設計 & セルフレビュー: US-201 ウェブサイトへのメモ（notes）機能

対象プロダクト: **umami** / 担当: test-engineer
入力: `docs/requirements/requirement-US-201.md`, `docs/specifications/api-specification.md`, `docs/implementation/implementation-notes-US-201.md`

本書は US-201「登録済みウェブサイトへの自由記述メモ（notes）」の **E2E テスト観点・シナリオ・受入条件トレーサビリティ**をまとめ、Playwright テストの設計根拠を記録する。実装本体・受入条件ファイルは変更していない。

## 1. テスト戦略

### 1.1 スコープと方針（テストピラミッド）

US-201 は既に**ユニット/コンポーネントテスト（`src/tests` 配下、16 件）**で以下を担保済み（実装メモ参照）。

- zod スキーマの正規化・境界値（`notes-route.test.ts`）
- 一覧セルの描画・省略（`WebsitesTable.test.tsx`）
- 編集フォームの入力・送信ブロック（`WebsiteEditForm.test.tsx`）

E2E はテストピラミッドを尊重し、**「実サーバ（Next.js App Router）+ 実 DB を通した end-to-end のふるまい」でしか担保できないクリティカルユーザージャーニー**に集中する。具体的には次の 2 層。

1. **API 契約 E2E**（`tests/e2e/api-website-notes.spec.ts`）
   実際の `POST /api/websites/{id}` 経由で、zod → `updateWebsite` → Prisma → DB → GET 再取得までの往復を検証する。ユニットではモックしていた **DB 永続化・認可（`canUpdateWebsite`/`canViewSharedWebsite`）・後方互換**を実機で確認する。
2. **UI E2E**（`tests/e2e/notes-website.spec.ts`）
   ブラウザ（Chromium）で編集フォームへの入力・保存・**再読み込み後の永続化**、および一覧での**省略表示 / 未設定時の非表示**という、ユーザーが実際に触れる体験を検証する。

E2E で「全 AC の全分岐」を再検証しようとはしない（フレーキーとメンテコストを避ける）。クライアント側の細かな上限カウンタ等の Should 項目は対象外。

### 1.2 既存資産の再利用

- 既存の Playwright 基盤（`playwright.config.ts`、`testIdAttribute: 'data-test'`）をそのまま利用。
- 既存 `tests/e2e/helpers.ts` の `loginPage` / `loginViaApi` / `authHeaders` を再利用し、認証は API ログイン + `localStorage` 注入で高速・安定化。
- notes 用に helpers へ**再利用可能なフィクスチャ関数**を追加（`createWebsite` / `getWebsite` / `updateWebsite`。生 response を返し、成功・失敗の両ステータスをテスト側で検証可能にした）。

### 1.3 安定性（フレーキー対策）方針

- **ロールベース/アクセシブルセレクタと `data-test` を優先**。脆い CSS/XPath には依存しない（notes 欄 = `data-test="input-notes"`、一覧セル = `data-test="cell-notes"`）。
- **web-first assertion（自動待機）を徹底**し、明示的 `sleep` を一切使わない（`toBeVisible` / `toHaveValue` / `toHaveCSS` / `toHaveAttribute`）。
- **テストデータ独立**: 各 spec は `Date.now()` サフィックス付きの一意なサイトを `beforeAll` で生成し、`afterAll` で削除。他テスト・並列実行に依存しない。
- 一意名で対象行を `filter({ has: ... })` して特定し、既存データ量に依存しない。
- 失敗時は `playwright.config.ts` の `trace: 'on-first-retry'` によりトレースを保存（原因追跡可能）。

## 2. テスト観点（正常系 / 異常系 / 境界値 / 権限 / 状態遷移 / 互換）

| 観点 | 内容 | 主対象 AC |
| --- | --- | --- |
| 正常系（保存） | メモ入力→保存→フィードバック→再読込で保持 | AC-1.1, AC-1.2 |
| 状態遷移（上書き） | 既存メモ→別内容へ上書き保存 | AC-1.3 |
| 境界（空/空白） | 空・空白のみ→トリムして未設定(null) | AC-1.4, Q5 |
| 境界値（上限） | 500 は許可 / 501 は不許可（サーバ 400・クライアントブロック） | AC-2.1, AC-2.2, AC-2.3 |
| 一覧表示 | メモありは省略表示（1行 truncate）、フルはホバー(title) | AC-3.1, AC-3.2, Q6 |
| 一覧非表示 | メモ未設定サイトは要素自体を出さない | AC-3.3 |
| 権限（更新） | 更新権限なしユーザーの更新は 401 | AC-4.1, AC-4.2 |
| 権限（閲覧） | 閲覧権限なしユーザーの取得は 401 | AC-4.3 |
| 後方互換 | 新規サイトは notes=null、未指定更新で既存値保持 | AC-5.1, AC-5.2, AC-5.3 |

## 3. E2E シナリオ一覧

### 3.1 API 契約 E2E — `tests/e2e/api-website-notes.spec.ts`（serial）

`beforeAll` で管理者ログイン + テスト用サイト作成、`afterAll` で削除。

| # | シナリオ | 手順（要旨） | 期待 | AC |
| --- | --- | --- | --- | --- |
| A1 | 新規サイトの notes 既定値 | 作成直後に GET | `notes === null` | AC-5.1/5.3 |
| A2 | 保存と上書き | POST notes="First" → POST notes="Second" | 各 200、body.notes が反映 | AC-1.1/1.3 |
| A3 | 永続化（GET 往復） | POST 後に GET 再取得 | 保存値が返る | AC-1.2 |
| A4 | 上限 500（許可） | POST 500 文字 | 200、長さ 500 | AC-2.1/2.3 |
| A5 | 上限超過 501（拒否） | POST 501 文字 | 400 | AC-2.2/2.3 |
| A6 | トリム後判定 | POST "空白+500文字+空白" | 200、トリム後 500 で保存 | AC-2.3, Q5 |
| A7 | 空文字→null | POST notes="" | 200、`notes===null` | AC-1.4, Q5 |
| A8 | 空白のみ→null | POST notes="   \n  " | 200、`notes===null` | Q5 |
| A9 | 明示 null→未設定 | POST notes=null | 200、`notes===null` | AC-1.4 |
| A10 | 未指定で既存保持 | notes 設定後、name のみ POST | 200、name 更新 & notes 保持 | AC-5.2 |
| A11 | 権限なし更新は 401 | 別ユーザー（role=user, 非所有）で POST notes | 401、値は不変 | AC-4.1/4.2 |
| A12 | 権限なし閲覧は 401 | 別ユーザーで GET | 401 | AC-4.3 |

> A11/A12 は `beforeAll` で更新権限のない一般ユーザーを作成→そのユーザーのトークンで対象サイト（管理者所有）にアクセス。`afterAll` でユーザー削除。

### 3.2 UI E2E — `tests/e2e/notes-website.spec.ts`（serial, Chromium）

`beforeAll` で「メモあり用」「メモなし用」2 サイトを一意名で作成、`afterAll` で削除。各テスト `beforeEach` でログイン。

| # | シナリオ | 手順（要旨） | 期待 | AC |
| --- | --- | --- | --- | --- |
| U1 | 入力・保存・再読込で保持 | 設定画面で notes 入力→保存 | 「Saved.」トースト→reload で値保持 | AC-1.1/1.2 |
| U2 | 上書き | 既存値確認→別値で保存→reload | 新値が保持 | AC-1.3 |
| U3 | クリア（空保存） | notes を空にして保存→reload | エラーなし、空で保持 | AC-1.4, Q5 |
| U4 | 500 文字保存 | 500 文字入力→保存→reload | 保存成功・値保持 | AC-2.1 |
| U5 | 501 文字ブロック | 501 文字入力 | 検証メッセージ表示 or 送信不可、**保存されない**（baseline 維持） | AC-2.2 |
| U6 | 一覧の省略表示 | 複数行メモ保存→一覧表示 | `cell-notes` 表示、title=フル本文、`white-space:nowrap`/`text-overflow:ellipsis` | AC-3.1/3.2, Q6 |
| U7 | 一覧の非表示 | メモなしサイト行を確認 | `cell-notes` が 0 個（プレースホルダも無し） | AC-3.3 |

> U5 は「無効値が保存されないこと」を主眼に、送信ボタン無効化 / 検証メッセージのいずれの実装でも成立する堅牢なアサーションにしている（`.or()` で両対応、送信可能な場合のみクリックしてメッセージを確認）。

## 4. 受入条件トレーサビリティ（網羅度）

| AC | 内容 | カバーするシナリオ | 種別 |
| --- | --- | --- | --- |
| AC-1.1 | 入力・保存＋フィードバック | U1, A2 | UI + API |
| AC-1.2 | 再読み込みで保持 | U1, A3 | UI + API |
| AC-1.3 | 上書き保存 | U2, A2 | UI + API |
| AC-1.4 | 空→未設定（null） | U3, A7, A9 | UI + API |
| AC-2.1 | 500 文字は許可 | U4, A4 | UI + API |
| AC-2.2 | 501 文字は拒否（400 / クライアントブロック） | U5, A5 | UI + API |
| AC-2.3 | 境界=500（500可/501不可、トリム後判定） | A4, A5, A6 | API |
| AC-3.1 | 一覧でメモ確認可 | U6 | UI |
| AC-3.2 | 長文は省略表示（レイアウト非破壊） | U6 | UI |
| AC-3.3 | 未設定は一切表示しない | U7 | UI |
| AC-4.1 | 権限なしの更新は認可エラー | A11 | API |
| AC-4.2 | サイト更新権限と同一ルール | A11 | API |
| AC-4.3 | 閲覧はサイト閲覧権限準拠 | A12 | API |
| AC-5.1 | 既存（未設定）サイトがエラーなく動作 | A1, U7 | API + UI |
| AC-5.2 | 未指定更新で notes 保持 | A10 | API |
| AC-5.3 | notes は nullable/optional | A1 | API |
| Q5 | トリム/空白のみは未設定 | U3, A6, A7, A8 | UI + API |
| Q6 | 改行可・一覧は1行省略 | U6 | UI |

**網羅度**: US-201 の全受入条件（AC-1.x〜AC-5.x）および確定事項 Q5/Q6 を E2E でカバー。
Q2（共有ページ非露出）は共有ページ経路が別実装であり、ユニット/設計で担保済みのため E2E 対象外（過剰な E2E 肥大を避ける方針）。Q1（500=length 準拠）は API 境界テスト A4/A5 で実質担保。

## 5. 実行方法・前提

```bash
# 前提: umami アプリ + DB が起動していること（既定 http://localhost:3000）
#   認証情報は helpers.ts の umamiUser（既定 admin/umami）または環境変数で上書き。
#   例: UMAMI_USER / UMAMI_PASSWORD / UMAMI_USER_ID / PLAYWRIGHT_BASE_URL

# 既存 webServer 設定（pnpm dev 自動起動）を使う場合
pnpm test:e2e

# 既に起動済みサーバに対して実行する場合
PLAYWRIGHT_SKIP_WEB_SERVER=1 PLAYWRIGHT_BASE_URL=http://localhost:3000 pnpm test:e2e

# US-201 のみ
pnpm test:e2e api-website-notes.spec.ts notes-website.spec.ts
```

- テストデータは各 spec が自己完結で生成/削除するため、事前シードは不要（`admin` ユーザーのみ前提）。
- `--list` によるコレクションはローカルで確認済み（8 ファイル / 53 テスト、うち US-201 は 19 テスト）。実行は稼働中の umami + DB が必要。

## 7. セルフレビュー

### 7.1 E2E / Playwright チェックリスト

- [x] セレクタは `data-test` / ロール・アクセシブル名基準（脆い CSS/XPath に非依存）
- [x] 明示的 `sleep` を排し、web-first assertion（自動待機）を使用
- [x] テストは一意データ + `beforeAll`/`afterAll` の生成・後始末で独立（並列/順序非依存）
- [x] テストデータの生成と後始末が閉じている（サイト・ユーザーを削除）
- [x] 失敗時にトレースを保存（`trace: 'on-first-retry'`）
- [x] クリティカルフローに集中し E2E が肥大化していない（境界の網羅はユニット層に委譲）

### 7.2 良い点

- API 契約と UI の 2 層で、DB 永続化・認可・後方互換という**モックでは検証できない end-to-end のふるまい**を実機確認。
- 権限テスト（A11/A12）で「非所有ユーザーは更新も閲覧も 401」を直接検証し、AC-4 を実機で担保。
- U5 は実装差異（送信ボタン無効化 or 検証メッセージ）に対して堅牢な設計で、フレーキーになりにくい。

### 7.3 懸念・改善余地（今回対象外）

- **実行には稼働中の umami + DB が必要**。CI では `docker-compose` 等での DB 起動が前提（既存 e2e と同条件）。本フェーズはテスト設計・実装が対象のため CI ワークフロー追加は行っていない。
- 一覧の truncate は CSS プロパティ（`white-space`/`text-overflow`）の適用で検証。ピクセル単位のはみ出し検証（視覚回帰）は対象外。
- Q2（共有ページ非露出）の E2E は共有ページ経路の別実装ゆえ本設計では対象外とした（設計/ユニットで担保）。将来、共有ページ側の回帰防止として最小 1 ケース追加の余地あり。
