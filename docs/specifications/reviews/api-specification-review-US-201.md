# API 設計レビュー結果: US-201

- 対象: `docs/specifications/api-specification.md` §2（ウェブサイトのメモ）
- レビュー観点: 一貫性 / セキュリティ / 後方互換 / テスト容易性

---

## 1. 良い点

- 専用エンドポイントを新設せず既存 `POST /api/websites/{websiteId}` を拡張する方針は、
  要件のスコープ（対象外: 専用 API 新設）と一致し、権限・キャッシュ経路を再利用できる。
- エラー形式を既存 `src/lib/response.ts` / `parseRequest` に完全準拠させており、
  テストが期待すべき JSON 構造（`error.properties.notes.errors`）が明確。
- 上限検証をクライアント/サーバ二重化し、バイパスを 400 で拒否する点が NFR-2 に合致。

## 2. 指摘・懸念と対応

| # | 懸念 | 対応 / 判断 |
| --- | --- | --- |
| A-1 | `notes` を `optional` にすると「省略＝変更なし」と「明示的クリア」が曖昧 | `undefined`（省略）=変更なし、`""`/空白/改行=`null` へ正規化、`null`=クリア、と明示的に定義（§2.3 表）。テストは 3 経路を区別 |
| A-2 | zod `.max(500)` の数え方 | zod は文字列長をコードポイントで評価。OQ-1（コードポイント）に一致。DB は `VARCHAR(500)`（文字数）で二重担保 |
| A-3 | 権限チェックの順序 | `canUpdateWebsite` を getWebsite 等の前段で評価し 401 を返す既存順序を踏襲（AC-7） |
| A-4 | 文字数超過の文言をサーバが返すか | zod の `.max(500, { message })` で同一文言を返し、UI 表示文言（4.4）と一致させる |

## 3. 代替案と却下理由

- **代替1: メモ専用エンドポイント `PATCH /api/websites/{id}/notes` を新設。**
  却下理由: 要件スコープ外。権限・監査・キャッシュ無効化を二重に実装することになり、
  退行リスクと保守コストが増える。
- **代替2: 空文字をそのまま保存（NULL 正規化しない）。**
  却下理由: OQ-2 の決定（トリム後空は未設定）に反し、一覧の「メモ有無」判定が
  空文字と NULL で分岐して複雑化する。

## 4. 結論

方針を承認。実装フェーズは §2.3 の入力別挙動表と §4.5 のエラー契約を満たすこと。
