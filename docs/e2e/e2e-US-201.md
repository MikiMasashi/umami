# E2E テスト設計書 US-201: ウェブサイトへのメモ（Notes）機能

このドキュメントは `docs/requirements/requirement-US-201.md`（受入条件 AC-1〜AC-10）、
`docs/specifications/api-specification.md`、`docs/implementation/implementation-notes-US-201.md`
を基点に設計した E2E テストの観点・シナリオと、受入条件との対応（トレーサビリティ）をまとめる。
実行可能な Playwright テストは `tests/e2e/website-notes.spec.ts`（UIシナリオ）と
`tests/e2e/api-website-notes.spec.ts`（APIシナリオ）に実装した。

## 1. テスト観点（テスト対象の切り口）

1. **入力・保存の正常系**: 設定編集画面からメモを入力し保存できること、保存後の永続化。
2. **入力値の境界・異常系**: 500文字境界（500文字はOK/501文字はNG）、クライアント側・サーバー側の二重バリデーション。
3. **空値の扱い**: メモが任意項目であり、空文字での保存が成功すること。
4. **一覧表示**: メモあり／長いメモの省略表示／メモなしの3パターンでの一覧描画。
5. **後方互換性**: メモ未設定（`null`）の既存ウェブサイトが、一覧・詳細・メモ以外の更新でエラーにならないこと。
6. **認可（更新）**: `canUpdateWebsite` 相当の権限を持たないユーザーがメモを変更できないこと（UI操作不可 or API 401/403）。
7. **認可（閲覧）**: 更新権限がなくても、既存の閲覧権限モデルに従えばメモを閲覧できること。

振る舞いの差異（例: クライアント側は送信ブロック、サーバー側は400応答）を明示的に区別して確認する。

## 3. AC-9 / AC-10（権限まわり）のテスト設計について

`src/permissions/website.ts` の実装を確認したところ、`canUpdateWebsite` は次の3系統で判定される。

- 管理者（`isAdmin`）: 常に許可
- 個人所有（`website.userId === user.id`）: 所有者であれば**ロールに関わらず**許可
- チーム所有（`website.teamId`）: チームメンバーであり、かつそのチームロールが
  `PERMISSIONS.websiteUpdate` を持つ場合のみ許可（`ROLE_PERMISSIONS[team-view-only] = []` のため
  `team-view-only` ロールは更新不可）

一方 `canViewWebsite` はチームメンバーであれば**ロールを問わず**閲覧を許可する。

この非対称性（更新はロール依存、閲覧はメンバーであれば可）を利用し、以下の実運用に即したシナリオで
AC-9/AC-10 を検証する。

1. 管理者がチームを作成し、そのチームにメモ付きウェブサイトを所属させる。
2. 管理者が一般ユーザーをチームロール `team-view-only`（閲覧専用相当）で招待する。
3. そのユーザーでログインし、
   - メモの更新を試みると `POST /api/websites/:id` が **401** を返し、メモは変更されないこと（AC-9）を確認する。
   - `GET /api/websites/:id` ではメモを含む情報が取得できること（AC-10）を確認する。

この設計により、モックではなく実際の権限判定ロジック（チームロールと `ROLE_PERMISSIONS`）を通した
End-to-Endの検証になっている。なお、UIレベルでの「編集操作ができない」という代替受入条件（AC-9）は、
本設計ではAPIレベルの401検証で担保する方針とした（UIの編集不可表示は独立したUI要素の存在確認になり、
本フェーズではAPI水準の防御確認を優先した。将来的にUI側の非表示/無効化の見た目を追加検証してもよい）。

## 4. Playwright テスト実装

- `tests/e2e/website-notes.spec.ts`: UIを操作するE2Eシナリオ（AC-1, 2, 3, 4, 5, 6, 7, 8）。
  既存の `tests/e2e/website.spec.ts` と同じ `loginPage` / `addWebsite` / `deleteWebsite` ヘルパーパターンを踏襲。
- `tests/e2e/api-website-notes.spec.ts`: APIを直接呼び出すE2Eシナリオ（AC-1, 2, 3, 4, 8, 9, 10）。
  既存の `tests/e2e/api-website.spec.ts` のパターン（`loginViaApi` + `request` フィクスチャ）を踏襲。
- `tests/e2e/helpers.ts` を拡張し、以下を追加した（既存関数のシグネチャは後方互換を維持しつつ拡張）。
  - `addWebsite` に第5引数 `options?: { notes?, teamId? }` を追加し、レスポンスボディを返すよう変更（既存呼び出し元は影響を受けない）。
  - `addUser` / `addTeam` がレスポンスボディを返すよう変更（既存呼び出し元は戻り値を使用していないため影響なし）。
  - `updateWebsite`: `POST /api/websites/:id` を呼び出す薄いラッパー（新規）。
  - `addTeamUser`: `POST /api/teams/:id/users` でチームメンバーを追加する薄いラッパー（新規）。

## 5. 追加ライブラリ

**なし。** 本プロジェクトには Playwright（`@playwright/test`）がすでに導入・設定済み
（`playwright.config.ts`、既存の `tests/e2e/*.spec.ts`）であり、新規のテスト用ライブラリは追加していない。
既存の `helpers.ts` / `fixtures.ts` のパターンを拡張する形で実装した。

## 6. セルフレビュー

- **網羅性**: AC-1〜AC-10のすべてに対し、最低1つ以上のテストケースが対応していることをトレーサビリティ表で確認した。
- **既存パターンとの整合性**: 既存の `website.spec.ts` / `api-website.spec.ts` と同じヘルパー関数・`data-test`属性
  （`input-notes`, `button-submit`, `link-button-edit` 等）を使用し、実装（`WebsiteEditForm.tsx`,
  `WebsitesTable.tsx`, `route.ts`）の実際のテスト属性・DOM構造と整合させた。
- **静的検証**: `npx tsc --noEmit` でテストファイルに型エラーがないこと、`npx playwright test --list` で
  16件（UI 8件・API 8件）のテストが正しく列挙されること、`npx biome lint` でリントエラーがないことを確認済み。
  実際のブラウザ・DB環境での実行（`pnpm test:e2e`）は本フェーズの検証環境では未実施のため、実装フェーズ／
  CI環境での実行を推奨する。
- **クリーンアップ**: 各テストで作成したウェブサイト・ユーザー・チームは `afterAll`/明示的な `delete*` 呼び出しで
  後始末し、テスト間の副作用を防止した。
- **権限テストの妥当性**: AC-9/AC-10は実際の権限判定ロジック（`src/permissions/website.ts` の
  チームロールベースの判定）に依存する形で設計し、モックに頼らず実挙動を検証する構成とした
  （詳細は「3. AC-9 / AC-10のテスト設計について」を参照）。
- **懸念・フォローアップ事項**:
  - AC-6（省略表示）のレイアウト崩れ確認は `boundingBox()` の高さ検証という簡易的な手段に留めている。
    ピクセル単位の厳密なビジュアルリグレッションが必要な場合は、別途スクリーンショット比較の導入を検討する。
  - AC-9のUIレベル（編集操作自体ができないことの画面確認）は本設計では未実装。UI上でメモ入力欄が
    非表示・無効化されるようになった場合は追加のUIシナリオを検討する。
  - 要件書「疑問点」に記載の通り、省略表示の具体文字数（40文字）は実装フェーズの裁量値であるため、
    実装が変更された場合はテストの想定文字数調整が必要になる可能性がある。
