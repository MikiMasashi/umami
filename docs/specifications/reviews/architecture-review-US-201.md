# 全体アーキテクチャ設計レビュー結果 (US-201)

## 1. レビュー観点

- 既存レイヤードアーキテクチャ（UI / API / 権限 / データアクセス / DB）への整合性
- 変更範囲の最小化（NFR-1: 既存の実装スタイルへの準拠）
- 保守性・将来拡張性とのバランス

## 2. 懸念点と検討

### 懸念点1: 変更をUI・API・DBの3層に閉じることの妥当性

- **懸念**: 権限層・データアクセス層に一切手を入れないことで、将来「メモだけ別権限にしたい」「メモの変更履歴を残したい」等の要求が来た際に大幅な手戻りが発生しないか。
- **検討**: 要件定義書の対象外（2.2節）に「メモの変更履歴・バージョン管理」が明記されており、現時点でその設計を先取りする必要はない（YAGNI原則）。また権限モデルもFR-9で「既存の`canUpdateWebsite`に相当する権限モデル」への準拠が明記されているため、新設は不要と判断できる。
- **結論**: 現状のレイヤー構成のまま、既存の関数・パターンを最大限再利用する設計を採用する。将来の変更履歴要件が具体化した時点で、`WebsiteNoteHistory` のような別テーブル・別サービスとして追加する拡張の余地は残されている（`notes` カラム自体は現在値のみを保持するシンプルな設計のため、履歴テーブルを後から追加しても矛盾しない）。

### 懸念点2: フロントエンドの一覧表示コンポーネントの責務配置（省略表示ロジックをどこに置くか）

- **代替案A**: APIレスポンス側で切り詰め済み文字列を返す（サーバー側で省略処理）。
- **代替案B（採用）**: クライアント側（`WebsitesTable.tsx` またはその配下の表示コンポーネント）で切り詰め処理を行う。
- **検討**: サーバー側で切り詰めると、詳細画面用の全文取得と一覧用の切り詰め文字列取得とでAPIを分岐する必要が生じ、NFR-3（既存レスポンス互換性）に反する複雑化を招く。既存アーキテクチャでは「一覧・詳細ともに同じ `Website` オブジェクトを描画側で表示形式に整形する」パターン（例: `DateDistance` コンポーネントによる日付の相対表示）が採用されており、これに倣うのが自然である。
- **結論**: 表示整形はクライアント側（Reactコンポーネント）の責務とし、APIは常に完全な `notes` を返す設計を採用した。

### 懸念点3: 権限層・データアクセス層を変更しないことによるテスト容易性への影響

- **懸念**: `src/permissions/website.ts` の既存テスト（例: 類似する `board.test.ts` のようなテストファイル）に`notes`関連のテストケースが必要にならないか。
- **検討**: 権限判定ロジック自体は変更していないため、既存の権限テストで`canUpdateWebsite`の正常系・異常系がカバーされていれば、`notes`更新時の権限テストは「APIレベルの結合テスト」として `POST /api/websites/:websiteId` に `notes` を含むリクエストを送るケースを追加すれば十分と判断した。
- **結論**: 権限層の単体テスト追加は不要。API層のテスト（実装フェーズで作成）にてカバーする方針を申し送る。

### 懸念点4: フロントエンドの`TextArea`コンポーネント採用の妥当性（frontend-engineer観点）

- **懸念**: `@umami/react-zen` に複数行入力向けコンポーネントが存在するか、既存の`TextField`で代替できないか。
- **検討**: `@umami/react-zen` パッケージの型定義（`node_modules/@umami/react-zen/dist/index.d.ts`）に `TextArea` コンポーネントの存在を確認済み。既存の`TextField`は単一行入力用であり、FR-1「複数行のテキスト入力欄」の要件を満たすには`TextArea`が適切。
- **結論**: `TextArea`コンポーネントを採用し、`rows`属性等で表示行数を制御する設計とした。既存の`FormField`ラッパーパターン（`label`, `name`, `rules`）はそのまま踏襲でき、UIコンポーネントライブラリの一貫性を損なわない。

### 懸念点5: 一覧表示のレイアウト崩れ防止策の設計粒度

- **懸念**: 「省略表示によりレイアウトが崩れない」（要件定義書 関連ユーザーストーリー記載）という非機能要求に対し、アーキテクチャ設計としてどこまで規定すべきか。
- **検討**: 具体的なCSS実装（`text-overflow: ellipsis`等）は実装の詳細であり、アーキテクチャ設計では「列の最大幅を固定し、はみ出したテキストは省略表示するという表示契約」を規定するに留め、具体的なピクセル数・切り詰め文字数は実装フェーズの裁量とする。
- **結論**: 表示契約（列幅固定＋省略表示）をAPI仕様書内に明記し、詳細な実装値は実装フェーズに委ねる。

## 3. 却下した代替案のまとめ

| 代替案 | 却下理由 |
|---|---|
| メモ専用の権限層・履歴テーブルを事前設計 | 要件定義書で明示的にスコープ外とされており、YAGNI原則に反するため見送り |
| サーバー側で一覧用に切り詰めたnotesを返す専用API | 既存のレスポンス互換性・シンプルなAPI設計方針に反し、複雑化するため不採用 |
| `TextField`での複数行入力代用 | 複数行入力要件（FR-1）を満たせないため不採用、`TextArea`を採用 |
| 権限層への単体テスト追加 | 判定ロジック自体が無変更のため、API結合テストでのカバーで十分と判断 |

## 4. 実装フェーズへの申し送り事項

- 一覧表示の省略表示の具体的な文字数・ツールチップ表示要否は要件定義書「疑問点2」に記載の未確定事項であり、実装時に確認・決定すること。
- Share（共有）ビューでのメモ表示可否（要件定義書「疑問点3」）は、本設計では「既存の閲覧権限モデルに準拠」という前提を置いているが、運用ポリシー確定後に再確認が必要な場合はアーキテクチャ仕様書を更新すること。
