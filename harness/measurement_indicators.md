# 測定指標一覧（修了制作 / 検証ハーネス）

添付プレゼン「修了制作.pptx」の **P13〜P16** で設計された「本プロジェクトで測定する指標」を表にまとめ、
併せて **現状ハーネスで実装済みの計測** を調査し、各指標が **どこからどこまでを測っているのか（ユーザー目線）**
を対応づけたもの。

- 出典スライド: P13=評価の骨格 / P14=①効率カード / P15=②品質カード / P16=③自動化率カード
  （ユーザー指示は「P13〜15」だが、指標カードは③自動化率がP16に続くため、設計の完全性を保つためP16も含めた）
- ★ = 発表で用いる**主指標**（P13の骨格図で指定。青＝押し上げる力／緑＝守る対象）

## 検証の骨格（P13）

> **自動化率↑・効率↑ でも 品質は"維持"されるか** を検証する。

| 立場 | 意味 | 中心となる主指標 |
|------|------|------------------|
| 押し上げる力（青） | 自動化率↑・効率↑ | 人時比率 / 自動化率、コードレビュー省略率、人手レビュー時間 |
| 守る対象（緑） | 品質は維持が目標（既存と同等以上） | 受入条件充足率、標準偏差 / 変動係数 |
| 核心の問い | レビュー省略率↑で欠陥・デグレは増えないか | 「**コードレビュー省略率 × 残存欠陥・デグレ**」のペアが提案プロセスの成否を直接示す |

## 実装状況の凡例

| 記号 | 意味 |
|------|------|
| ✅ | **自動計測 実装済み**（`.harness/metrics.jsonl` 等に自動記録される） |
| 🟡 | **部分実装 / 導出可能**（生データは取得済みだが、指標としての集計・算出は未実装） |
| ⚙️ | **手動運用**（仕組み上は人が記録する前提。自動計測なし） |
| 🔴 | **未実装**（計測手段・対象プロセスがまだ無い） |

> ハーネスが現在自動で持つ生データは2本。
> **`metrics.jsonl`**（フェーズ実行ごと1行: 実験条件の来歴・実行時間・ターン数・
> ツール呼び出し数・トークン量・コスト）と **`reviews.jsonl`**（レビューラウンドごと1行:
> レビュー時間・レビュー対象数・指摘件数）。どちらも巻き戻し時は `rolled_back=true` が付く。
> 集計・統計・網羅度・欠陥検出などの上位指標を出すスクリプトは現時点で存在しない
> （`Invoke-Process.ps1` が生ログを吐くところまで）。
>
> **保存先**: worktree ローカルの `.harness/` と、メインリポジトリ側の **`.harness-data/`** への
> 二重書き。集計に使うのは後者（worktree を削除しても残る）。全行が `sample`（サンプルID）を
> 持つため、10サンプル分をそのまま1ファイルとして読める。
>
> 列の一覧と定義は [harness/README.md](README.md) の「計測される項目」を参照。
> **実行エージェント（Claude / Copilot）を切り替えても列と定義は同一**であり、その担保方法は
> [measurement_parity.md](measurement_parity.md) にまとめてある。

| 手戻り | 差し戻し回数・手戻り時間 | ゲート不合格→再実行の回数と所要時間（state.json） | — | 🟡 | **回数**＝`metrics.jsonl`の`phase`末尾が`-revise`の行数で導出可（記録済み）。**時間**＝その`-revise`行の`duration_ms`（AI再実行時間）で取得済み。ただし件数集計・「ゲート不合格判定」自体は人手依存で、自動サマリは未実装。 |

## 現状ハーネスで「自動的に測れているもの」まとめ（ユーザー目線の測定範囲）

`Invoke-Process.ps1` が `Agents.ps1` 経由でエージェント（`claude` / `copilot`）を実行し、
その出力ストリームから拾って `metrics.jsonl` へ**フェーズ実行ごとに1行**追記する。

| フィールド | 何を測っているか | 測定の開始点 → 終了点 | 対応する設計指標 |
|-----------|------------------|------------------------|-------------------|
| `duration_ms` | そのフェーズのAI実行の実時間（**ハーネス計測**） | エージェント起動 → プロセス終了 | リードタイム/フェーズ別実行時間（①）、手戻り時間（①） |
| `input_tokens` / `output_tokens` / `total_input_tokens` | 投入・生成したトークン量 | 同フェーズの実行全体 | **生成AI利用料（①）の一次指標**（PPT定義「トークン量×単価」の前半） |
| `cost_native` / `cost_unit` | そのフェーズの課金の生値と単位（`usd` / `aiu`） | 同上 | 生成AI利用料（①）※**通貨が違うためエージェント横断では比較しない** |
| `num_turns` / `tool_calls` | LLM往復回数・ツール呼び出し回数（**ハーネス計測**） | 同フェーズ内 | （PPT指標に直接対応なし・参考値。自律性の傍証） |
| `agent` / `model` / `agent_version` / `harness_commit` | 実験条件の来歴（エージェント・**実行時に解決されたモデル実体**・CLIバージョン・ハーネスのSHA） | 各フェーズ実行時 | 条件が同一であることの証拠。集計時の分類キー |
| `model_overridden` / `harness_dirty` | 実験条件からの逸脱フラグ（`-Model` 上書き / 未コミットのハーネス改変） | 各フェーズ実行時 | `true` の行は本番の分布から除外する |
| `phase`（`-revise`） | 差し戻し再実行の回数・時間の識別 | `-Revise`実行ごとに`<id>-revise`行を追加 | 差し戻し回数・手戻り時間（①）、ゲート一発通過率（③） |
| `rolled_back` | 巻き戻し済み試行の除外フラグ | `-Rollback`時に該当行へ付与 | 標準偏差・変動係数の集計時に最終試行のみ数えるため（②） |
| `is_error` / `session_id` / `ts` / `story` / `variant` | 実行の成否・追跡・条件識別 | 各フェーズ実行時 | 集計時の分類キー |
| `sample` | サンプルID（`existing-claude-3`） | `-Init` 時に確定・全行に付与 | **同一 variant の10サンプルを区別する集計キー**（②③はこれが無いと成立しない） |

`reviews.jsonl` へは**1レビューラウンドごとに1行**追記される（ゲートを `-Continue` /
`-Revise` で閉じた時点）。列の一覧は [harness/README.md](README.md) の「レビュー（人手レビュー時間の計測）」を参照。

| フィールド | 何を測っているか | 測定の開始点 → 終了点 | 対応する設計指標 |
|-----------|------------------|------------------------|-------------------|
| `review_ms` | **人手レビュー時間（主指標）** | `-Review` がPENDINGレビューを作った瞬間（GitHub打刻） → 「Submit review」（GitHub打刻） | 人手レビュー時間（①）、人的工数（①）、人時比率・自動化率（③） |
| `read_ms` / `write_ms` | 読み込み時間 / 指摘を書いていた時間 | 開始→初回コメント / 初回コメント→提出 | 参考値。`write_ms` は旧#11定義でパイロットPRと接続でき、感度分析に使う |
| `latency_ms` | 承認ラグ（人がPCの前に座るまでを含む壁時計時間） | ゲート停止（ローカル時刻） → 提出 | 参考値。**レビュー時間ではない**ので主指標に使わない |
| `comments` | 人間の指摘件数（自動返信を除外） | 当該ラウンドのレビュー | 指摘密度（①）の分子 |
| `diff_files` / `diff_added` / `diff_deleted` | レビュー対象の規模 | フェーズのベースSHA → HEAD | レビュー対象数（①） |
| `outcome` / `round` | 合格か差し戻しか・ラウンド番号 | ラウンドを閉じたコマンド | 差し戻し回数（①）、ゲート一発通過率（③） |
| `review_time_source` | 計測の由来（`pending-review` / `first-comment` / `missing` / `skipped`） | — | **欠測（`missing`）と省略（`skipped`）を混同しないための識別子**。③レビュー省略率の分子は `skipped` |
| `rolled_back` | 巻き戻し済みラウンドの除外フラグ | `-Rollback`時に該当行へ付与 | 集計時に最終試行だけを数えるため |

> `agent_duration_ms` / `api_duration_ms` / `agent_num_turns` は**エージェントの申告値**であり、
> 計測区間の定義がエージェント間で揃わない。突合用の参考値として併記しているだけなので、
> **指標の算出には使わないこと**（主指標は上表のハーネス計測値）。

**測定範囲の重要な境界（誤解しやすい点）:**

- `duration_ms` は **AIが動いている時間のみ**。ゲートで停止して人がレビューしている時間、
  `-Continue` を叩くまでの待ち時間は**一切含まない**。人手側は `reviews.jsonl` の
  `review_ms` が担当する（両者は別ファイル・別の時計で測っている）。
- `review_ms` は**レビューを開いてから提出するまで**であり、`latency_ms`（ゲート停止から提出までの
  壁時計時間）とは別物。実サンプルにはゲートが6日間開いていた例があり、壁時計時間を主指標にすると
  「実験者がいつPCの前に座ったか」を測ることになる。
- `review_ms` は `-Review` の運用が守られて初めて実値になる。`review_time_source` が
  `first-comment` の行は**過小評価**（読み込み時間を取りこぼす）、`missing` の行は**欠測**。
  集計時は必ずこの列で層別すること。
- 「総リードタイム」「手戻り回数」「ゲート一発通過率」「標準偏差」は
  **生データはあるが集計スクリプトが未実装**（🟡）。集計器を1本足せば発表用の値になる状態。
- 品質系（受入条件充足率・Mutation・PCE・回帰・保守性）と③のレビュー省略率は
  **計測基盤そのものが未整備**（🔴）。特にコードレビュー省略率は**提案プロセス未実装**が前提ブロッカー。

## 実装の優先度メモ（一指標ずつ着手する際の目安）

1. **集計器を追加すれば取れる（🟡→✅）**: 総リードタイム、生成AI利用料合計、手戻り回数、
   ゲート一発通過率、標準偏差・変動係数、レビュー時間の群間比較・指摘密度・人時比率 …
   `metrics.jsonl` と `reviews.jsonl` を読む集計スクリプト1本で主指標の大半が揃う。
2. ~~**人手計測の仕組み化**~~ … `-Review`＋GitHubのサーバ打刻で実装済み（`reviews.jsonl`）。
   残る運用リスクは「`-Review` を経ずにPRを開く」「Submitし忘れる」の2点で、前者は
   `review_time_source`で識別、後者は`-Continue`/`-Revise`のガードで機械的に防いでいる。
3. **品質計測基盤の新規実装（🔴）**: 受入条件充足率（AC記入＋E2E判定連携）→ 回帰テスト合格率 →
   保守性指摘件数（Lint）→ Mutation Score → PCE の順で段階導入。
4. **提案プロセス実装（🔴・前提）**: `processes/proposed.json`＋`prompts/proposed/*.md`が無いと
   コードレビュー省略率（③の核）は測れない。

> 注意: `injected-defects.md`（欠陥注入＝仕込み欠陥検出率の枠組み）は残っているが、
> P15で「仕込み欠陥検出率は不採用」と決定されている。設計と実装資産の不整合として、
> 採否を確定させておくとよい（PCE/DREに一本化するか、注入欠陥を廃止するか）。
