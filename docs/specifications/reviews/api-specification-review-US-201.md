# API設計レビュー結果 US-201: ウェブサイトへのメモ（notes）追加

## 1. レビュー観点

- 既存 API の設計思想（部分更新・nullable フィールドの意味論）との整合性
- 権限制御（US-201-6）が確実に効くか
- バリデーション二重化（クライアント／サーバー）の実現可能性
- 後方互換性（US-201-5）

## 2. 懸念点と対応

### 懸念1: `notes` を空文字列で送った場合の意味論の曖昧さ
- **懸念**: フォームが空欄の場合、react-hook-form は `''` を返すのが一般的。API 側で `''` をそのまま保存すると「空文字列」と「null（未設定）」の2状態が生まれ、UI 側の「未入力時は非表示」判定が複雑になる。
- **対応**: API 層で `''` → `null` に正規化するルールを明記した（api-specification.md §2.2）。これにより DB 上は常に「null = 未設定」の1状態に統一される。
- **残存リスク**: 正規化ロジックはハンドラ内の実装詳細であり、実装時にトリム処理を忘れるとスペースのみの入力が「空でない」と誤判定される可能性がある。実装フェーズでのユニットテストで担保する前提とする。

### 懸念2: `notes` フィールド追加が既存の `Prisma.WebsiteUpdateInput` 型に対して型エラーを起こさないか
- **懸念**: `updateWebsite` の型シグネチャは `Prisma.WebsiteUpdateInput` を使用しており、スキーマ変更（`prisma/schema.prisma`）と API 実装は同じ PR 内で整合させる必要がある。
- **対応**: data-specification.md でスキーマ変更を先に定義し、`prisma generate` 実行後に型が自動反映される前提を明記。設計書の記述順序としてもデータ層→API層の依存関係を明示した。
- **結論**: 設計上の問題ではなく実装順序の話であり、対応方針は明確なため許容。

### 懸念3: 権限チェックの「閲覧はできるが編集不可」という要件（US-201-6）に対する設計十分性
- **懸念**: 受け入れ条件では「編集画面を開く（閲覧権限がある場合）→ メモは閲覧できるが編集・保存操作はできない」とあるが、これは主に UI 側（保存ボタンの無効化）の制御であり、API 設計だけでは「閲覧はできるが保存はできない」を完全に保証できない。
- **対応**: API 設計としては、サーバー側で `canUpdateWebsite` が false の場合は `unauthorized()` を返すことでバックエンド側の防御を保証する（画面操作を経由しない直接 API 呼び出しにも対応）。UI 側の保存ボタン無効化は frontend-engineer の実装範囲であることを architecture-specification.md に明記済み。
- **結論**: API 設計としては十分。UI 側の補完が必要な点は architecture-specification.md との役割分担として妥当。

## 3. 検討した代替案と却下理由（再掲・要点）

| 代替案 | 却下理由 |
|---|---|
| メモ専用エンドポイント新設 | 権限・エラーハンドリングの重複コストが既存の汎用更新エンドポイント拡張のメリットを上回らない。 |
| サーバー側のみのバリデーション | 要件の非機能要件で明示的にクライアント・サーバー両方の検証が求められているため不採用。 |
| GET レスポンスからの `notes` 除外 | 一覧・詳細双方での表示要件（US-201-1, US-201-3）を満たせなくなるため不採用。 |

## 4. 総合評価

既存の API 契約（部分更新・nullable セマンティクス）を破壊せず、最小の変更差分で US-201 の受け入れ条件（入力・永続化・バリデーション・権限・後方互換性）を満たせる設計と判断する。懸念点はいずれも実装フェーズでのユニットテストによって担保可能な範囲に収まっている。
