# API設計レビュー結果 US-201

## 懸念点

1. **`z.treeifyError` のエラーメッセージ文言への依存**
   zod のバージョンアップでエラーメッセージの文言が変わる可能性がある。テストで
   `properties.notes.errors[0]` の文言を完全一致で検証すると壊れやすい。
   → 対応: テストでは HTTP ステータス（400）と `error.code`（`bad-request`）、
   および `notes` が更新されていないことのみを検証し、`properties` 内の文言までは
   厳密一致させない方針とした（API仕様書に明記）。

2. **`canUpdate` フィールドをレスポンスに追加することの影響範囲**
   既存のAPIレスポンスにフィールドを1つ追加するだけであり、既存クライアントは未知のフィールドを
   無視するため後方互換性は壊れない。ただし、`canUpdate` の計算のために `GET` のたびに
   `canUpdateWebsite` を追加実行することになり、DBアクセス（`getTeamUser` 等）が発生しうる。
   → 対応: 非機能要件「一覧・詳細取得APIのレスポンス時間に有意な劣化を生じさせない」との
   兼ね合いで、`canUpdate` は **詳細取得APIのみ**に追加し、一覧APIには含めないことで
   影響範囲を最小化した（一覧行の編集は別画面遷移であり、一覧上での活性・非活性制御は不要）。

3. **代替案: `notes` 更新を専用エンドポイントに分離する案の再検討**
   専用エンドポイント化すれば「メモだけの部分更新」時の楽観ロック・競合検出が個別に設計しやすい
   というメリットはあるが、要件に変更履歴・同時編集の考慮は明記されていない（Won't スコープ）。
   → 却下を維持。過剰設計を避け、既存の更新APIに統合する方針を採用した。

4. **空文字列の正規化（`""` → `null`）をAPI層で行うかフロントエンドで行うか**
   フロントエンドでも空文字を送らずに `null` を送信する実装は可能だが、API層で正規化することで
   「どのクライアントから呼ばれても一貫した挙動になる」ことを優先し、API仕様書ではAPI層での
   正規化を明記した。ただし実装フェーズでの実装箇所（API層 or DB層のデフォルト変換）は
   実装者の裁量に委ねる（テストは「空文字列で保存 → 再取得すると `null` または空文字列として
   扱われ、一覧表示等でエラーにならない」という外部から観測可能な振る舞いのみを検証する）。

## 代替案・却下理由まとめ

| 代替案 | 却下理由 |
|---|---|
| メモ専用の `PATCH /api/websites/{id}/notes` エンドポイント | 要件スコープに見合わない過剰設計。既存の更新APIに統合するほうがシンプル |
| フロントエンドで独自に権限判定ロジックを再実装 | 権限ロジックの二重管理となり、既存の権限モデル一貫性の非機能要件に反する |
| `canUpdate` を一覧APIにも含める | 性能面の非機能要件（レスポンス時間の劣化防止）を優先し、詳細APIのみに限定 |

## 結論

上記の懸念点はいずれも「テストの記述に影響するかどうか」の観点で対応方針を確定済みであり、
API設計はテストコード作成に着手可能な状態にあると判断する。
