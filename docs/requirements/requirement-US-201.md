# 要件定義書 US-201: ウェブサイトへのメモ（notes）機能

## 1. 背景・目的

サイト運用者は umami に複数のウェブサイトを登録して運用しているが、サイトが増えると
「どれが本番でどれが検証用か」「誰の依頼で作成したか」といった管理上の文脈情報を、
サイト名やドメインだけでは判別できなくなっている。

本要件は、各ウェブサイトに自由記述の**メモ（notes）**を持たせることで、運用者が
サイトごとの背景情報を記録・参照できるようにし、サイト管理の効率と正確性を高めることを
目的とする。

### 対象ユーザー

- サイト運用者（ウェブサイトの編集権限を持つユーザー：Owner / 編集権限のあるチームメンバー）
- 閲覧のみ可能なユーザー（メモの閲覧は可能だが編集は不可、5章参照）

### 成功指標

- ウェブサイト編集画面からメモを登録・編集・保存でき、リロード後も内容が保持される。
- ウェブサイト一覧画面でメモの有無・内容（省略表示含む）を確認できる。
- 既存（メモ未設定）のウェブサイトの一覧表示・編集が引き続きエラーなく動作する。

## 2. スコープ

### 対象（In Scope）

- ウェブサイト（Website）エンティティへの `notes`（自由記述メモ）フィールドの追加。
- ウェブサイト編集画面（Settings → Websites → 対象サイトの編集画面）でのメモの入力・編集・保存。
- メモの永続化（DB保存、リロード後も保持）。
- ウェブサイト一覧画面でのメモの表示（省略表示、未入力時は非表示）。
- メモの文字数上限（500文字）のバリデーション（フロント・バック両方）。
- 既存ウェブサイト（メモ未設定 = null）との後方互換性維持。
- ウェブサイト更新権限に基づくメモ編集の権限制御。

### 対象外（Out of Scope）

- メモの検索・絞り込み機能（一覧のフィルタ条件としての利用）。
- メモの変更履歴・監査ログ（誰がいつ変更したか等）。
- メモに対するリッチテキスト／Markdown／添付ファイル等の高度な書式サポート（プレーンテキストのみ）。
- メモ内容の他システム（レポート、公開共有ダッシュボード等）への連携・出力。
- 複数言語対応（i18n の文言追加は既存の枠組みに乗せる程度に留め、翻訳作業自体はスコープ外）。
- メモに対する通知・アラート機能。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| メモ（notes） | ウェブサイトに紐づく自由記述のテキスト情報。運用者が任意に入力する補足情報。 |
| サイト運用者 | umami にウェブサイトを登録し、設定を編集する権限を持つユーザー。 |
| 更新権限 | 対象ウェブサイトに対して `update`（編集）操作が許可されている権限。既存の権限モデル（Owner/チームロール等）に準拠。 |

## 4. 機能要件

### FR-1: メモの保存領域追加

- **要件**: Website データモデルに `notes`（任意項目、文字列、上限500文字）を追加する。
- **根拠**: メモを永続化するためのデータの保存先が必要なため。
- **詳細**:
  - 既存レコードは `notes = null`（未設定）として扱う。
  - Prisma スキーマ、DB マイグレーション、API のレスポンス/リクエストの型に反映する。

### FR-2: メモの入力・編集・保存（編集画面）

- **要件**: サイト運用者として、ウェブサイト編集画面（Settings → Websites → 対象サイト編集）で
  メモを入力・編集・保存したい。なぜなら、サイトの背景情報を記録し後から参照したいから。
- **受け入れ条件**:
  - Given 更新権限を持つユーザーがウェブサイト編集画面を開いている
    When メモ欄に文字列を入力して保存する
    Then メモが保存され、成功メッセージ等の保存完了が確認できる。
  - Given メモが既に保存されているウェブサイト
    When 編集画面を開く
    Then 保存済みのメモが入力欄に表示される。
  - Given メモを編集して保存した
    When 画面をリロードする
    Then 保存したメモの内容がそのまま表示される（永続化されている）。
  - Given メモ未設定（null）の既存ウェブサイト
    When 編集画面を開く
    Then メモ欄は空欄で表示され、エラーは発生しない。
  - Given メモ欄を空にして保存する
    When 保存を実行する
    Then メモ未設定の状態として保存され、エラーにならない。

### FR-3: メモの文字数上限バリデーション

- **要件**: メモは500文字を上限とし、超える場合は保存できないようにしたい。なぜなら、
  メモが際限なく長くなることを防ぎ、一覧表示や運用上の見通しを保つため。
- **受け入れ条件**:
  - Given 編集画面でメモ欄に500文字ちょうどを入力する
    When 保存する
    Then 保存が成功する。
  - Given 編集画面でメモ欄に501文字以上を入力する
    When 保存を試みる
    Then 保存は行われず、バリデーションエラーが表示される（フロント側での入力チェック）。
  - Given フロント側の入力チェックを回避して501文字以上のリクエストが直接APIに送られた
    When サーバー側で処理する
    Then サーバー側のバリデーション（zod 等）で拒否され、DBには保存されない。

### FR-4: ウェブサイト一覧でのメモ表示

- **要件**: サイト運用者として、ウェブサイト一覧でも各サイトのメモの有無・内容を確認したい。
  なぜなら、一覧画面から各サイトの用途をすぐに把握したいから。
- **受け入れ条件**:
  - Given メモが設定されているウェブサイトが一覧に含まれる
    When 一覧画面を表示する
    Then そのサイトの行にメモの内容（または省略表示）が表示される。
  - Given メモの内容が一覧上の表示領域に収まらない長さである
    When 一覧画面を表示する
    Then メモは省略表示（例: 末尾を省略記号で切り詰め）される。
  - Given メモが未設定（null または空文字）のウェブサイトが一覧に含まれる
    When 一覧画面を表示する
    Then そのサイトの行にはメモに関する表示は何も出さない（プレースホルダー文言も表示しない）。

### FR-5: 既存ウェブサイトとの後方互換性

- **要件**: メモ未設定の既存ウェブサイトについても、一覧表示・編集・保存が従来どおりエラーなく
  動作すること。
- **受け入れ条件**:
  - Given メモ列を持たない状態で作成された既存のウェブサイトレコード（マイグレーション後は notes=null）
    When 一覧取得・詳細取得・編集画面表示・他フィールドの更新を行う
    Then いずれの操作もエラーにならず、従来と同じ挙動を維持する。

### FR-6: 更新権限に基づくアクセス制御

- **要件**: ウェブサイトを更新する権限がないユーザーはメモを書き換えられないようにしたい。
  なぜなら、権限のないユーザーによる不正確・意図しない情報変更を防ぐため。
- **受け入れ条件**:
  - Given ウェブサイトの更新権限を持たないユーザー（閲覧のみ等）
    When メモの保存APIを直接呼び出す、または編集UIから保存を試みる
    Then 403 相当のエラーとなり、メモは変更されない。
  - Given ウェブサイトの更新権限を持たないユーザー
    When 編集画面またはメモ表示箇所を閲覧する
    Then 既存のメモ内容は閲覧できる（読み取りは可、書き込みのみ制限）が、編集操作（入力・保存ボタン等）は無効化されているか実行できない。
  - Given 更新権限を持つユーザー
    When メモを編集・保存する
    Then 正常に保存できる（FR-2 のとおり）。

## 5. 非機能要件

| 分類 | 要件 | 根拠/優先度 |
|---|---|---|
| データ整合性 | メモは既存の Website 更新APIと同じトランザクション/検証フローに乗せ、他フィールドの更新と独立して不整合を起こさないこと。 | Must |
| セキュリティ | メモ入力値は既存のサニタイズ/エスケープ方針（XSS対策）に従い、一覧・編集画面での表示時にスクリプト実行等を許さないこと。 | Must |
| 入力検証 | フロント（zod スキーマ等）とサーバー側の両方で500文字上限を検証し、片方のみのバルデーションに依存しないこと。 | Must |
| 互換性 | 既存の Website API レスポンス・DBスキーマに対する非破壊的な変更（マイグレーションは追加のみ、既存カラムの変更・削除は行わない）。 | Must |
| 国際化 | UI文言は既存の i18n の枠組み（メッセージ定義ファイル等）に追加する形とし、他言語文言の欠落时でもキー表示等の破綻をしないこと。 | Should |
| パフォーマンス | 一覧画面でのメモ表示追加により、既存の一覧取得APIのレスポンス時間が体感できるほど劣化しないこと（追加カラム1つの取得程度の許容範囲）。 | Should |
| アクセシビリティ | メモ入力欄・一覧表示は既存の `@umami/react-zen` コンポーネント体系・アクセシビリティ水準に準拠すること。 | Should |
| 運用性 | マイグレーションは既存のマイグレーションフロー（Prisma Migrate）に従い、ロールバック手順を意識した設計とすること。 | Should |

## 6. ユーザーストーリー一覧

| ID | ストーリー | 優先度(MoSCoW) |
|---|---|---|
| US-201-1 | サイト運用者として、ウェブサイト編集画面でメモを入力・編集・保存したい。サイトの背景情報を記録し後から参照したいから。 | Must |
| US-201-2 | サイト運用者として、保存したメモがリロード後も保持されていてほしい。情報を失いたくないから。 | Must |
| US-201-3 | サイト運用者として、メモは500文字程度までに制限してほしい。メモが際限なく長くなるのを防ぎたいから。 | Must |
| US-201-4 | サイト運用者として、ウェブサイト一覧でも各サイトのメモを（省略されていても）確認したい。一覧からすぐにサイトの用途を把握したいから。 | Must |
| US-201-5 | サイト運用者として、メモ未設定の既存サイトも今までどおり問題なく扱えてほしい。運用中のサイトに影響を与えたくないから。 | Must |
| US-201-6 | サイト運用者として、更新権限のないユーザーにメモを書き換えられたくない。情報の正確性を守りたいから。 | Must |

## 7. 受け入れ条件まとめ（Given/When/Then）

上記 FR-2〜FR-6 の受け入れ条件を参照。要約すると以下を満たせば US-201 は受け入れ可能とする。

1. 編集画面でメモの入力・編集・保存・リロード後の保持ができる。
2. 500文字以内は保存でき、超える場合はフロント・サーバー双方で保存が拒否される。
3. 一覧画面でメモが（必要に応じて省略表示で）確認でき、未入力サイトには何も表示されない。
4. メモ未設定の既存サイトの一覧・編集操作がエラーなく従来どおり動作する。
5. 更新権限のないユーザーはメモを書き換えられない（閲覧は可）。

## 8. 前提・オープンクエスチョン（未決事項）

要望文からは判断できず、実装時に確認・仮決めが必要な事項を以下に整理する。

1. **文字数上限の厳密な値**: 要望では「500文字程度」と表現が曖昧。本要件では **500文字を上限（500文字は許可、501文字以上は不可）** と仮定する。厳密な数値の最終確認が必要な場合は関係者に確認すること。
2. **文字数のカウント方式**: 全角・半角、絵文字（サロゲートペア）等をどう1文字としてカウントするか（JavaScript の `.length` 基準か、書記素クラスタ基準か）は未指定。本要件では umami の他のテキスト項目（例: サイト名の `VarChar(100)` 等）と同様の一般的な文字数カウント方式に準拠する前提とし、詳細は実装時の既存パターンに合わせる。
3. **一覧画面での省略表示の具体的な文字数・表示形式**: 「長い場合は省略表示でよい」とのみ指定があり、具体的な省略文字数やツールチップでの全文表示の要否は未指定。本要件では省略表示の実現方法自体は実装判断に委ねる（省略記号での切り詰め等、UIコンポーネントの一般的な挙動に従う）。
4. **権限モデルの詳細**: 「更新する権限がないユーザー」が具体的にどのロール（Viewer/Member等）を指すかは、umami既存の権限モデル（チームロール、Owner等）にマッピングする前提とする。既存のウェブサイト更新API（他フィールド更新）と同一の権限チェックを踏襲することを前提とし、メモ専用の別権限は設けない。
5. **メモの表示位置（一覧画面内のどこに配置するか）**: 生の要望に具体的なカラム配置の指定がないため、UI設計時（フロントエンド実装フェーズ）に既存の一覧レイアウトとの整合を取る形で決定する。
6. **監査ログ・変更履歴の要否**: 要望に明記がないため、本要件ではスコープ外（対象外）と整理した。将来的に必要であれば別途要件化する。

以上の未決事項は、実装前に prescriptive な確認（関係者レビュー）を推奨するが、いずれも実装をブロックする重大な矛盾ではないため、上記の仮定に基づき要件を確定する。
