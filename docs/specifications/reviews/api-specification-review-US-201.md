# API仕様レビュー結果: US-201（ウェブサイトへのメモ機能）

## レビュー観点と結論

| 観点 | 判定 | コメント |
|---|---|---|
| 既存API契約への非破壊性 | OK | `notes` はリクエスト・レスポンス双方でoptionalなフィールド追加のみ。既存フィールドの型・意味・必須/任意区分は変更していない。 |
| 権限制御の一貫性 | OK | 新規の専用権限を設けず、既存の `canUpdateWebsite` / `canViewSharedWebsite` をそのまま適用する設計とした。FR-6（更新権限がない場合は403相当、閲覧は可）を、既存ロジックの再利用のみで満たせる。 |
| サーバー側バリデーション | OK | zod `.max(500).nullable().optional()` を追加。フロント側のチェックを回避した直接APIリクエストに対しても保存前に拒否される（FR-3の3つ目の受け入れ条件）。 |
| トランザクション境界 | OK | 既存の単一の `updateWebsite()` 呼び出し（内部は単一の `prisma.client.website.update()`）に `notes` を含めるのみで、他フィールド更新と同一トランザクションに乗る。専用トランザクションを新設しない。 |

## 懸念点

1. **`null` と `undefined` の意味の違いをAPI利用者にどう伝えるか**
   - 懸念: `notes: null` を「明示的にクリア」、キー省略（`undefined`）を「対象外」として区別する設計にしたが、現行フロントエンド実装は空文字送信のみを使う想定であり、`null` 送信の実利用パスが現時点でない。
   - 判断: 将来的なAPI利用者（他クライアント、将来のバルク編集機能等）のための拡張余地として型定義上は許容するが、本ストーリーのUI実装では使用しないこととし、過剰な作り込みを避けた。フロントエンドは空文字を送信し、サーバー側で `null` に正規化する経路のみを実装対象とする。

2. **一覧APIのレスポンスサイズ増加**
   - 懸念: 一覧取得時に全件で最大500文字の `notes` が付与されるため、大量サイトを持つテナントではレスポンスサイズが増加する。
   - 検討: 非機能要件で「追加カラム1つの取得程度の許容範囲」と明記されており許容範囲内と判断。将来的に一覧APIのレスポンス肥大化が問題になった場合は、一覧専用のフィールド選択（GraphQL的な部分取得、あるいは `select` によるnotes除外オプション）を別途検討する余地を残すが、本ストーリーではスコープ外とした。

3. **専用エンドポイント化を見送った判断の妥当性**
   - 検討: `PATCH /notes` のような専用エンドポイントも比較検討したが、権限チェック・バリデーションの二重実装コストと、非機能要件「データ整合性：既存の更新APIと同じトランザクション/検証フローに乗せる」という明示要件から、既存更新APIへの統合を採用。将来メモに関する専用の操作（監査ログ等、現状スコープ外）が必要になった場合は再検討する。

## 総合判定

**承認**。既存のWebsite更新・取得APIへの後方互換な拡張として、FR-1〜FR-6および非機能要件（データ整合性、入力検証、互換性）を満たすことを確認した。実装フェーズへ引き継ぐ。
