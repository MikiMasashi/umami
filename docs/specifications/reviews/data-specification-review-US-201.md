# データモデル／データベーススキーマ設計レビュー結果 US-201

## 懸念点

1. **`VarChar(500)` という物理制約とアプリケーション層の `max(500)` バリデーションの二重管理**
   DB制約とアプリケーション層のバリデーションの上限値がズレると、片方だけ通ってもう片方で
   失敗するという不整合が起きうる。
   → 対応: 両方とも「500」を単一の要件値としてドキュメント上でも明記し、実装フェーズで
   ズレなく実装されているかをコードレビューで確認する運用とする（本フェーズで自動テスト化は
   困難なため、設計ドキュメントに明記することで代替する）。

2. **既存カラム追加のマイグレーションの安全性**
   `NOT NULL` 制約なし・デフォルト値なしのカラム追加であるため、既存データへの影響はなく、
   ロールバックも容易。この点はリスクが低いと判断し、追加の検証タスク（バックフィル等）は
   不要と判断した。

3. **代替案: `notes` を別テーブル（`WebsiteNote`）に切り出す案の再検討**
   将来「メモの変更履歴」機能が追加された場合、別テーブルのほうが履歴管理しやすいという
   利点はある。しかし要件はそれを明確に Won't（対象外）としており、YAGNI の原則から
   時期尚早な抽象化を避け、単一カラム追加を採用した。将来的に履歴機能が必要になった場合は、
   その時点で `WebsiteNote` テーブルへの移行（マイグレーション）を検討すればよい
  （現時点でのカラム設計はその移行を妨げるものではない）。

4. **DBの種類（PostgreSQL/MySQL）ごとのスキーマファイルの差異**
   umami はデータベース種別ごとに `schema.prisma` を分けて管理している可能性がある
  （本レビュー時点でリポジトリ内の該当箇所は実装フェーズで確認・追随する前提とする）。
   本ドキュメントでは「両方に同一の変更を適用すること」を明記し、実装フェーズでの見落としを
   防ぐ注意書きとした。

## 代替案・却下理由まとめ

| 代替案 | 却下理由 |
|---|---|
| `WebsiteNote` 別テーブルに切り出す | 1:1属性であり、変更履歴等の要件がない現状ではJOINコストが増えるだけで利点がない（YAGNI） |
| `notes` を汎用 `Json` 属性カラムに含める | 型安全性・バリデーションの簡潔さを優先し、既存の `domain` と同様の専用カラムを採用 |

## 結論

DBスキーマ変更はカラム追加のみのシンプルな変更であり、後方互換性・性能面のリスクは低いと
判断した。テスト設計・テストコード作成に着手可能な状態にある。
