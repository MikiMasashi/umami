# API設計レビュー結果: US-201

対象: `docs/specifications/api-specification.md`（US-201 部分）
レビュアー: backend-architect（+ frontend-engineer 観点）
判定: **承認（実装可）**。以下の懸念・代替案・却下理由を記録する。

---

## 1. 懸念点と対応

### C-1: トリムと文字数上限の適用順序（中）
- **懸念**: `.max(500)` を trim 前に適用すると、前後空白込みで501になり本文500でも弾かれうる。逆に trim 後判定なら本文500ちょうどを正しく許可できる。
- **決定**: **trim → その後に長さ判定**。zod では `z.string().transform(v => v?.trim()).refine(v => v.length <= 500)` あるいは `.max(500)` を transform 後の値に対して効かせる構成。境界（500/501）は trim 後の文字数で判定（AC-2.3）。
- **代償**: `.max()` を素直に書けず transform/refine の順序に注意が必要。実装者向けに本仕様3.2へ明記済み。

### C-2: 空入力を `null` にするか空文字にするか（中）
- **懸念**: 「未設定」を `null` と空文字のどちらで表すかが曖昧だと、一覧の「何も出さない」判定（AC-3.3）や後方互換（AC-5）で分岐が増える。
- **決定**: trim 後空なら **`null` に正規化して保存**。表示層は `null`/空 両方を「メモなし」と扱い防御的に実装。
- **根拠**: Q5。`null` 一本化で DB 上の状態が一意になり、既存の未設定（`null`）と区別不要になる。

### C-3: `notes: undefined`（未指定）の意味（低）
- **懸念**: Prisma は `undefined` フィールドを無視するため、未指定なら既存値保持で AC-5.2 を満たす。ただし `null` 送信時は明示的に「未設定へクリア」となり挙動が異なる。
- **決定**: 3値を区別する契約とする。undefined=変更なし / null or 空=クリア / 文字列=上書き。本仕様3.3に条件付きスプレッドで明記。

### C-4: 共有ページへの漏洩リスク（高）
- **懸念**: GET `/api/websites/{id}` が Website 全体を返すため、共有トークン経由の閲覧経路に `notes` が混入すると Q2（非公開）に反する恐れ。
- **確認結果**: 共有ページは別経路・最小フィールドで描画される想定。**本更新 API/取得 API に `notes` を足しても、共有ページ側のレスポンス構築に `notes` を明示追加しない限り露出しない**。実装時に共有系レスポンスへ `notes` を足さないことをレビュー必須項目とする。
- **決定**: 承認。ただし実装 PR で共有系レスポンスの差分がないことを確認する条件付き。

## 2. 代替案と却下理由

| 代替案 | 内容 | 却下理由 |
| --- | --- | --- |
| 専用エンドポイント `PATCH /websites/{id}/notes` | メモ更新を独立 API 化 | 認可・キャッシュ・フォーム送信を二重管理することになり、既存の単一 POST 経路（`canUpdateWebsite` 済み）と重複。AC-4.2「サイト更新と同一経路」に反する。**却下**。 |
| `notes` を必須（non-optional）に | スキーマを厳格化 | 後方互換（AC-5.2）を破壊し、既存クライアントの更新が失敗する。**却下**。 |
| クライアント検証のみで上限担保 | サーバ zod を省略 | API 直叩き（AC-2.2/4.1）で回避可能になり要件違反。**却下**。 |
| trim をクライアントのみで実施 | サーバは生値保存 | クライアントを信頼できない。サーバ正規化が正準（Q5）。**却下**。 |

---

## 3. 残リスク / フォローアップ
- `.max` と `.transform` の順序は実装で誤りやすい。契約テスト（500=200 / 501=400 / 空=null）で担保する。
- 将来メモを複数化・履歴化する場合は本 API を破壊せず、別リソース（`/websites/{id}/notes` コレクション）として追加する拡張余地を残す。
