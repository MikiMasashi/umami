# API Specification Review (US-201)

## 結論
- 承認（軽微な運用注意あり）。

## 懸念点
1. `notes` の空文字を許可すると、一覧の「表示あり/なし」判定が画面ごとにぶれる可能性がある。
2. 文字数超過時のエラーメッセージ文言が既存翻訳キー未整備だと UX が不統一になる。

## 代替案と却下理由
1. **代替案**: `PATCH /api/websites/[websiteId]/notes` を新設する。  
   **却下理由**: 権限・バリデーション・キャッシュ更新導線が二重化し、既存実装パターンから逸脱するため。
2. **代替案**: 一覧 API で `notesExcerpt` を返し、UI はそれを表示する。  
   **却下理由**: 省略ルール変更のたびに API 変更が必要になり、UI 表示責務との分離が崩れるため。

## 採用時のガード
1. 保存時に空文字を `null` 正規化し、表示条件を単純化する。
2. 400 応答は既存エラー形式を維持し、クライアント側のエラーハンドリング変更を最小化する。
