# データモデル／データベーススキーマ設計レビュー結果 (US-201)

## 1. レビュー観点

- NFR-2（既存の命名規則への準拠）、NFR-4（500文字保持可能なデータ型）、NFR-5（既存マイグレーション運用への準拠）との整合性
- 既存ウェブサイトデータとの後方互換性（FR-8, AC-8）

## 2. 懸念点と検討

### 懸念点1: カラム名を `notes`（複数形）にするか `note`（単数形）にするか

- **代替案A**: `note`（単数形。1件のメモという意味合いを強調）
- **代替案B（採用）**: `notes`（複数形）
- **検討**: 要件定義書内で「メモ（Notes）」と英語表記が明記されており、機能名としても「Notes機能」と呼称されている。umami本体の他モデルでも自由記述系のフィールドは複数形にする慣習は明確ではないが、要件定義書のブリーフに合わせて `notes` を採用した。
- **結論**: `notes` を採用。要件定義書の表記との一貫性を優先。

### 懸念点2: `@map` によるDBカラム名とPrismaフィールド名の分離要否

- **検討**: 既存の `Website` モデルでは `resetAt` → `reset_at`、`userId` → `user_id` のように、キャメルケースのPrismaフィールド名をスネークケースのDBカラム名に `@map` している。しかし `name`、`domain` のような単語1つのフィールドは `@map` を使用せず、DBカラム名もそのまま `name`/`domain` である。
- **結論**: `notes` も単語1つのフィールドであるため、既存パターン（`name`/`domain`）に倣い `@map` を付与しない。これはNFR-2（既存の命名規則に倣う）に沿った判断である。

### 懸念点3: カラム長を500文字ちょうどにするか、余裕を持たせるか（例: 600, 1000文字）

- **代替案A**: `VARCHAR(600)` 等、余裕を持たせる。
- **代替案B（採用）**: `VARCHAR(500)`。
- **検討**: 要件定義書「疑問点」セクションに「500文字ちょうど、または512文字などDB都合の値を持たせるか未確定」と明記されている。しかし機能要件FR-4は「メモの最大文字数は500文字とし、超過した場合は...保存を拒否する」と明確にアプリケーションレベルでの上限を500文字と定めている。
- **結論**: アプリケーション側のバリデーション上限（500文字）とDBカラム長を完全に一致させることで、「DB制約とアプリ制約の二重の防御線」を最もシンプルな形で実現できるため、余裕を持たせずに `VARCHAR(500)` を採用した。将来的に上限文字数を変更する場合は、マイグレーションとzodスキーマの両方を同時に変更する運用とする。
- **却下理由（代替案A）**: 余裕を持たせる場合、「DBには保存できるがアプリケーションバリデーションでは拒否される」中間状態が生まれ、直接API経由で上限超過データが紛れ込むリスク（バリデーションのバイパス、データ移行時の直接INSERT等）を生む可能性があるため採用しなかった。

### 懸念点4: `TEXT` 型を採用しない理由

- **代替案**: 長さ制限のない `TEXT` 型 + アプリケーション側バリデーションのみで文字数を制御する。
- **検討**: PostgreSQLでは `VARCHAR(n)` と `TEXT` のパフォーマンス差はほぼ無いとされるが、DBスキーマ自体に上限を明示することで「スキーマを見ただけで仕様上限が分かる」という可読性・保守性のメリットがあり、既存の `domain VARCHAR(500)` パターンとも一貫する。
- **結論**: `VARCHAR(500)` を採用し `TEXT` は採用しない。

### 懸念点5: 既存データへのマイグレーション時の影響

- **検討**: `ALTER TABLE "website" ADD COLUMN "notes" VARCHAR(500);` は新規カラム追加のみであり、デフォルト値も指定しないため、既存の全レコードは自動的に `NULL` になる。ロック時間・パフォーマンスへの影響は他のカラム追加マイグレーション（例: `20_add_heatmap` 等）と同等で、無視できるレベルと判断した。
- **結論**: 追加のみのシンプルなマイグレーションとし、データバックフィル処理は行わない（AC-8: 既存ウェブサイトの後方互換動作を保つため、`NULL` のままで問題ない）。

## 3. 却下した代替案のまとめ

| 代替案 | 却下理由 |
|---|---|
| カラム名を `note`（単数形） | 要件定義書の表記（「メモ（Notes）」）との一貫性を優先し `notes` を採用 |
| `@map` でDBカラム名を分離 | 既存の`name`/`domain`と同様、単語1つのフィールドは`@map`なしとする命名規則に統一 |
| `VARCHAR(600)`等、余裕を持たせたカラム長 | アプリ層とDB層のバリデーション上限を完全一致させ、バイパスによる不整合データ混入を防止するため500文字ちょうどを採用 |
| `TEXT`型の採用 | スキーマ上の可読性・既存の`domain`カラム設計との一貫性を優先 |
| マイグレーション時の既存データへのデフォルト値設定 | 後方互換性の要件上、`NULL`のままで問題なく、不要な複雑性を避けるため |

## 4. 実装フェーズへの申し送り事項

- Prismaマイグレーション適用後は `npx prisma generate` を実行し、型定義を再生成する必要がある（実装フェーズで対応）。
- 文字数上限の最終確定値（500文字 vs 512文字等）は要件定義書「疑問点1」に記載の通り未確定事項であり、関係者確認の上で変更が必要になった場合は、本ドキュメントとAPI仕様書の両方を同時に更新すること。
