# API Specification Review: US-201

## セルフレビュー結果

### 採用案

既存 Websites API に `notes` を追加し、`GET /api/websites*`、`GET /api/websites/{websiteId}`、`POST /api/websites/{websiteId}` の既存契約を拡張する設計を採用した。

根拠:

- メモは Website 設定情報の一部であり、既存の参照・更新権限と一致する。
- 一覧表示で追加リクエストを発生させず、N+1 を避けられる。
- 既存の `useWebsiteQuery`、`useUserWebsitesQuery`、`useUpdateQuery` と cache touch を流用できる。

### 懸念点

| 懸念 | 評価 | 対応 |
| --- | --- | --- |
| 一覧 API のレスポンスサイズが増える | 最大 500 文字 x ページ件数の増加に限定される | 追加リクエストを避けるメリットを優先。ページング済み一覧でのみ返す。 |
| `POST /api/websites` 作成時にメモを受け付けないため、作成直後入力は 2 手順になる | US-201 の必須範囲は編集画面での入力・保存 | 作成フォームまで広げると UI スコープが増えるため MVP では除外。 |
| 空文字と `null` の扱いが実装者により揺れる | 表示条件や後方互換に影響する | API 保存時に `null` へ正規化し、レスポンス契約も `string | null` に統一。 |
| zod の文字数単位が Unicode grapheme ではない可能性 | 要件は既存の文字列長検証単位に従う前提 | 既存 zod スタイルに合わせ、独自文字数カウンタは導入しない。 |

### 代替案と却下理由

| 代替案 | 却下理由 |
| --- | --- |
| `PATCH /api/websites/{websiteId}/notes` を新設する | 権限・取得・保存が Website 設定と同一で、メモだけを別 resource にするほど独立性がない。API surface が増える。 |
| 一覧 API では `notes` を返さず、行ごとに詳細 API を呼ぶ | 一覧で N+1 リクエストになり、性能要件に反する。 |
| 一覧 API では省略済み `notesPreview` のみ返す | 編集画面と一覧でフィールドが分かれ、同期・型定義が複雑になる。UI 省略で十分。 |
| `notes` を作成 API でも受け付ける | 将来的には自然だが、US-201 の範囲外。作成フォーム変更まで含めると影響範囲が広がる。 |

### フロントエンド観点レビュー

- 既存 hook のレスポンスに `notes` が入るため、画面側は追加の loading/error state を持たずに済む。
- 一覧では `notes` 未設定時に DOM を出さない設計にしたため、メモなしサイトの表示ノイズを増やさない。
- 長文省略を API ではなく UI 責務にしたため、編集画面では常に全文を扱える。

### 結論

API 設計は US-201 の入力・保存・再表示・一覧表示・権限制御・500 文字検証を満たす。追加エンドポイントを作らない方針は、既存構造との一貫性と実装コストのバランスが最もよい。
