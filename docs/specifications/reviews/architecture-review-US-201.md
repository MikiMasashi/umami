# 全体アーキテクチャ設計レビュー結果 US-201

## 懸念点

1. **「テスト容易性の契約」に子コンポーネント分割を含めないことのリスク**
   契約を「外から観測できるもの（URL・DOM・HTTP）」に限定した結果、実装フェーズがどのように
   `WebsiteEditForm` の内部を分割してもコンポーネントテストは通る設計になっている。これは
   意図した設計（後続フェーズの実装の自由度を確保するため）だが、裏を返すと「メモ入力欄が
   `WebsiteEditForm` ではなく全く別の予期しない場所に実装される」といった大きな逸脱までは
   防げない。
   → 対応: ルーティング契約（どのページモジュールで検証するか）と `data-test`/表示文言の契約に
   よって、少なくとも「どの画面のどの見た目で」メモ機能が提供されるべきかは固定しているため、
   実用上のリスクは許容範囲と判断した。

2. **`canUpdate` フラグ導入によるフロントエンドの権限表示ロジックの単純化リスク**
   フロントエンドは `canUpdate` の真偽値のみを見て入力欄の活性・非活性を切り替える設計とした。
   これにより、フロントエンド側での複雑な権限判定ロジックが不要になる一方、`canUpdate` の
   計算自体はサーバー側の `canUpdateWebsite` に一本化されるため、権限ロジックの実装ミスが
   あった場合は API 全体に影響する（単一障害点になる）。
   → 対応: 既存の `canUpdateWebsite` は他の更新系エンドポイント（削除・リセット・転送等）でも
   既に利用されている実績のある関数であり、新規に権限ロジックを実装するわけではないため、
   リスクは許容範囲と判断した。

3. **代替案: メモ入力を別画面・別フォームに分離する案の再々検討**
   既存の `WebsiteEditForm` への統合を採用したが、これにより1つのフォームの責務
  （name/domain/notesの保存）がわずかに増える。将来的にメモ関連の機能（全文検索、リッチテキスト等）
   が追加された場合は、専用フォームへの分離を再検討する余地を残す。
   → 現時点では要件のスコープ（プレーンテキストの自由記述のみ）に対して既存フォームへの統合が
   最もシンプルであるため、この方針を採用した。

## 代替案・却下理由まとめ

| 代替案 | 却下理由 |
|---|---|
| メモ入力を別画面・別フォームに分離 | 要件のスコープでは既存フォームへの統合が最もシンプルで、保存導線が1つで完結する |
| コンポーネントテストの契約に子コンポーネントの分割方針まで含める | 実装フェーズの裁量を奪い、「レビュー済みテストを変更しない」という制約と衝突するため除外 |

## 結論

テスト容易性の契約は「外部から観測可能なもの」に限定して確定できており、E2E・コンポーネント
テストの双方を実装なしで記述するための土台が整っていると判断する。
