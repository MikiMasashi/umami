# 全体アーキテクチャ設計レビュー結果: US-201

対象: `docs/specifications/architecture-specification.md`（US-201 部分）
レビュアー: backend-architect（+ frontend-engineer 観点）
判定: **承認（実装可）**。以下の懸念・代替案・却下理由を記録する。

---

## 1. 懸念点と対応

### C-1: 一覧への `notes` 表示によるレイアウト崩れ（中 / FE観点）
- **懸念**: `WebsitesTable` は name/domain/created の固定カラム構成。長文メモ・改行入りメモでテーブルが崩れる恐れ（AC-3.2）。
- **決定**: メモは **1行 truncate（ellipsis）**で表示し、改行はレンダリング前に空白へ潰す。専用カラム追加時は固定/最大幅を設定。未設定は要素自体を描画しない（AC-3.3）。
- **代償**: 一覧で全文は読めない（詳細/編集画面で全文確認）。要件（省略表示）に合致。

### C-2: 一覧カラム追加の可否（中 / FE観点）
- **懸念**: 独立カラムを足すか、name セル配下に副次テキストとして出すかで見た目とソート挙動が変わる。
- **決定**: MVP は **既存テーブルにメモの省略表示を追加**（独立カラム or name 副次行のいずれか、既存 DataTable の表現力に合わせる）。メモのソート・フィルタは付けない（Won't）。表示/非表示トグルは Could のため MVP 対象外。
- **根拠**: Q4（Settings→Websites のみ対象）、優先度サマリ。

### C-3: 共有ページ経路への波及（高）
- **懸念**: 一覧・詳細の描画経路が共有（公開）ページと一部コンポーネントを共有していると `notes` が漏れる恐れ（Q2）。
- **決定**: メモ表示は **運用者向けの Settings/編集経路に限定**し、共有ページのコンポーネント・API レスポンスに `notes` を追加しない。実装時に共有経路の差分ゼロを確認する。

### C-4: i18n 文言の追加漏れ（低）
- **決定**: `labels.notes`（入力ラベル）、必要なら文字数超過の `messages` を `src/components/messages.ts` と `public/intl/messages/*.json`（少なくとも en-US）へ追加。ハードコード禁止。

### C-5: クライアント/サーバ二重検証の整合（低）
- **決定**: 上限500はクライアント（UXガイド, Should）とサーバ zod（正準）双方に置くが、**正準はサーバ**。両者の値（500）を定数化してドリフトを防ぐことを推奨。

## 2. 代替案と却下理由

| 代替案 | 内容 | 却下理由 |
| --- | --- | --- |
| メモ編集用の独立画面/モーダルを新設 | 専用 UI フロー | name/domain と同じ編集フォームで完結でき、AC-4.2「同一経路」にも合致。新画面は保守対象を増やすだけ。**却下**。 |
| サービス層/ユースケース層を新設 | API とクエリの間に抽象追加 | 単一フィールドの受け渡しに新レイヤは過剰（YAGNI）。既存の route→queries 構造で十分。**却下**。 |
| 一覧でメモ全文表示＋折り返し | truncate しない | レイアウト崩れ（AC-3.2 違反）。**却下**。 |
| メモ表示を全ダッシュボード一覧へ展開 | 表示箇所を拡張 | Q4 で Settings→Websites に限定確定。スコープ拡大は不要。**却下**。 |
| クライアント検証のみ | サーバ検証省略 | API 直叩きで上限回避可能（AC-2.2）。**却下**。 |
