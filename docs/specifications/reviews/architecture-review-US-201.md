# アーキテクチャレビュー結果: US-201（ウェブサイトへのメモ機能）

## レビュー観点と結論

| 観点 | 判定 | コメント |
|---|---|---|
| レイヤ責務の一貫性 | OK | データ層・クエリ層・権限層・APIルート層・フロントエンドの各層で、既存の責務分担を崩さずに `notes` を1本通す設計になっている。新規レイヤ・新規コンポーネント種別は導入していない。 |
| 依存方向 | OK | フロントエンド → API → 権限/クエリ → DB の一方向依存を維持。ビジネスルール（500文字上限、null正規化）はAPIルート層に集約し、フロントは表示・簡易バリデーションに徹する設計とした。 |
| 既存コンポーネントの再利用 | OK | `updateWebsite()` / `canUpdateWebsite()` / `useWebsiteQuery` 等、既存の関数・フックをそのまま利用でき、変更が必要な箇所を最小限（zodスキーマ、フォーム、テーブル）に絞れている。 |
| 非機能要件の網羅 | OK | データ整合性・セキュリティ・入力検証・互換性・国際化・パフォーマンス・アクセシビリティ・運用性の8項目全てに対応方針を明記した。 |

## 懸念点

1. **フロントエンドの権限ガード実装箇所が未確定**
   - 懸念: 「更新権限がないユーザーは編集操作を無効化」（FR-6）の具体的な実装箇所（`WebsiteEditForm` 自体か、呼び出し元の設定ページか）を本設計では確定していない。
   - 対応方針: 既存の umami フロントエンドが既に何らかの権限による表示切り替え（Owner/Viewer等でのUI出し分け）を持っている前提とし、そのパターンを踏襲する方針のみを明記した。実装フェーズで既存の権限ガードの実装箇所（例: 設定ページの読み取り専用モード分岐）を確認し、メモ欄固有の特別分岐を増やさないことを設計方針として明示した。これは実装詳細であり、アーキテクチャ設計としては「既存パターンに合わせる」という方針決定に留めることが適切と判断した。

2. **一覧画面での省略表示の具体的な実装コンポーネント**
   - 懸念: `@umami/react-zen` に文字列省略表示のための標準コンポーネント（例: Tooltip付きEllipsisText）が存在するかどうかは本設計時点で未調査。
   - 対応方針: 要件定義書 8章-3 で「UI実装時に決定する方針」と確認済みのため、アーキテクチャ設計では「CSSの `text-overflow: ellipsis` 等、既存パターンに準拠する」という方向性のみを示し、コンポーネント選定は実装フェーズのfrontend-engineer観点の詳細検討に委ねた。過度に詳細な実装決定をこの段階で行うと、実装時の既存コンポーネント調査結果と齟齬が生じるリスクがあるため。

3. **メモ列の一覧画面での配置位置**
   - 懸念: `domain` 列の後という暫定案を示したが、確定はしていない。
   - 対応方針: 要件定義書 8章-5 で「UI設計時（フロントエンド実装フェーズ）に決定する」との方針が確認済みであるため、本設計では暫定位置のみ提示し、最終配置は実装フェーズでの既存レイアウトとの整合確認に委ねることとした。

## 却下した代替案（要約と選定理由）

- メモ専用の新規リソース・専用ページ化 → 独立したライフサイクルを持たないため過剰設計として却下。
- フロントエンド専用の状態管理（新規ストア）追加 → 既存の React Query ベースのキャッシュで十分カバーできるため却下。
- 非同期キューでの保存処理 → メモは小さいテキストで同期処理の非機能要件を満たすため不要と判断し却下。

## 総合判定

**承認**。既存アーキテクチャ（Prisma → クエリ層 → 権限層 → APIルート → フロントエンド）に対する最小限かつ非破壊的な拡張として、全体の一貫性・保守性を損なわない設計であることを確認した。3点の懸念（権限ガード実装箇所・省略表示コンポーネント・一覧配置位置）は要件定義書で「実装時判断」と明記済みの事項であり、アーキテクチャ設計としてはこれ以上の詳細化を行わず、実装フェーズに委ねることが適切と判断した。実装フェーズへ引き継ぐ。
