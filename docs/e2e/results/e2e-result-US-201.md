# E2E テスト実施結果 US-201: ウェブサイトへのメモ（notes）機能

本ドキュメントは `tests/e2e/website-notes.spec.ts` / `tests/e2e/api-website-notes.spec.ts`
（および既存 E2E スイート全体）を実際に実行した結果である。設計書は
`docs/e2e/e2e-US-201.md` を参照。`stories/US-201/acceptance-criteria.md` はこの検証では
参照していない。

## 0. 実行環境・手順

- アプリケーション: `pnpm dev`（Next.js/Turbopack、`http://localhost:3000`）
- DB: Postgres 15（Docker、`docker-compose.dev.yml` を新規作成してホストへポート公開し、
  `pnpm run build-db-client` → `pnpm run update-db`（`prisma migrate deploy`、
  `21_add_website_notes` を含む全21マイグレーション適用）→ `pnpm run check-db` で確認。
- 実行コマンド: `npx playwright test --workers=1`（Turbopack の同時コンパイルによる
  タイムアウトを避けるため、CI と同様に直列実行。並列実行(6 workers)では notes と無関係な
  複数テストがタイムアウトしたため、直列実行の結果を正式な結果として採用した）。
- DB は一度クリーン（`docker compose down -v` → マイグレーション再適用）にしてから最終実行し、
  他テストの残留データ（ユーザー名重複等）による偽陽性の失敗を排除している。
- 実装（`src`/`aprisma`）・テストコード（`tests/e2e`）は一切変更していない。

## 1. サマリ

- 実行テスト数: 52件（US-201 関連 18件 + 既存スイート 34件）
- 結果: **29 passed / 16 failed / 7 did not run**（直列 `test.describe` 内で先頭が失敗すると
  以降は未実行になる Playwright の仕様による）
- US-201（notes機能）関連 18 シナリオ中: **10 passed / 8 failed**
- 検出した欠陥・不整合: 大きく2種類
  1. **テストフィクスチャの不整合（実装ではなくテスト側の問題）**: `tests/e2e/helpers.ts` の
     `addWebsite()` がウェブサイト**作成時**に `notes` を渡せる設計になっているが、
     `docs/specifications/api-specification.md` §1 の設計では `notes` は
     **更新エンドポイント（`POST /api/websites/:websiteId`）にのみ**追加する方針であり、
     実装（`src/app/api/websites/route.ts` の作成用 POST）も仕様通り `notes` を
     受け取らない。そのため `addWebsite(..., notes)` で作成した「メモ付き新規サイト」の
     メモは実際には保存されず、これに依存する複数のテスト（S2, S4, S7, S8, S10, S13, S16,
     S17）が失敗する。**実装は API 仕様書どおりであり、この点は実装の欠陥ではなく
     テストフィクスチャ（`addWebsite` ヘルパーとその呼び出し側）の前提の誤り**と判断した。
  2. **実装側の潜在的な欠陥（1件）**: 501文字以上のメモを入力すると保存ボタンは無効化され
     保存はブロックされる（機能的には正しい）が、要件（FR-3(2)）が求める
     「エラー表示」（画面上の検証エラーメッセージ）が表示されない。詳細は 3-2 節参照。
- 上記1のフィクスチャ問題を除けば、メモの**編集画面からの入力・保存・リロード後の永続化・
  境界値（500/501文字）・API契約・権限制御の基本フロー**は正しく動作していることを確認した
  （S1, S3, S5, S9, S11, S12, S14, S15, S18 が成功）。
- US-201 と無関係な既存スイート（`login.spec.ts` / `user.spec.ts` / `website.spec.ts` /
  `api-user.spec.ts` の一部）にも失敗が見られたが、これらは notes 機能と無関係な既存の
  環境/実装差異（例: ログイン後の遷移先が `/dashboard` ではなく `/websites` になっている等）
  であり、本タスクのスコープ外として概要のみ記録する（4節）。

## 3. 検出した欠陥・不整合の詳細

### 3-1. テストフィクスチャの不整合（`addWebsite` ヘルパーの前提誤り）

- **事象**: `tests/e2e/helpers.ts` の `addWebsite(request, auth, name, domain, notes?)` は
  `POST /api/websites`（作成）に `notes` を含めて送信する設計になっている
  （`...(notes !== undefined && { notes })`）。
- **実際の実装**: `src/app/api/websites/route.ts` の `POST`（作成用）の zod スキーマは
  `name` / `domain` / `shareId` / `teamId` / `id` のみを受け付け、`notes` は定義されておらず、
  `createWebsite()` に渡す `data` オブジェクトにも `notes` は含まれない。そのため
  作成時に `notes` を送っても**サーバー側で黙って無視され、保存されない**。
- **仕様との整合性確認**: `docs/specifications/api-specification.md` §1 の対象エンドポイント表を
  確認したところ、`notes` の追加対象は
  `GET /api/websites/:websiteId` / `POST /api/websites/:websiteId`（更新） /
  `GET /api/websites`（一覧）の3つのみであり、**作成用エンドポイント（`POST /api/websites`）は
  対象に含まれていない**。つまり実装は API 仕様書どおりに作られており、
  **実装の欠陥ではない**。
- **影響**: `addWebsite(..., notes)` を使って「メモ付きで新規作成」した前提のテスト
  （S2, S4, S7, S8, S10, S13, S16, S17 の計8シナリオ）は、実際にはメモが空の状態の
  ウェブサイトに対してテストを行うことになり、期待値との不一致で失敗する。
- **切り分け**: 実際のユーザー操作フロー（サイト作成→編集画面でメモ入力→保存、
  S1 で検証）は正しく動作しており、単体でのメモ保存・取得（更新API経由、S11/S12/S14/S15）も
  正しく動作している。したがって **US-201 の実装自体に欠陥があるわけではなく、
  E2E テストのフィクスチャ用ヘルパーが実装（および承認済みAPI仕様）と噛み合っていない**
  という テスト設計上の不整合であると判断する。
- **指示に基づく対応**: 本タスクではテストコード・実装コードのいずれも変更しないため、
  修正は行わず、上記の切り分け結果を欠陥検出の記録として本ドキュメントに残す。

### 3-2. 501文字超のメモ入力時に検証エラーメッセージが表示されない（実装側の潜在的欠陥）

- **事象**: `tests/e2e/website-notes.spec.ts`
  「blocks saving and shows a validation error for notes over 500 characters (FR-3)」
  （S6）で、501文字のメモをテキストエリアに直接セットした後、保存ボタン（`button-submit`）が
  `disabled` のまま 30 秒経過してもクリック可能にならずタイムアウトした。
- **画面状態の確認**（Playwright のエラーコンテキスト/アクセシビリティスナップショットより）:
  テキストエリアには 501文字の値が実際にセットされており（react-hook-form の
  `maxLength` バリデーションルールが機能し、フォームを invalid と判定して保存ボタンを
  無効化していると考えられる）、**保存がブロックされること自体（FR-3(2)前半）は
  正しく機能している**。しかし、要件が求める「エラー表示」（例:
  「500 characters or less」等の検証エラーメッセージ）に該当するテキストは
  画面上に見当たらず、`page.getByText(/500 characters or less/i)` のアサーションに
  到達する前に、無効化されたボタンへの `click()` 自体がタイムアウトした。
- **切り分け**: `src/app/(main)/websites/[websiteId]/settings/WebsiteEditForm.tsx` の
  `notes` フィールドには `rules={{ maxLength: { value: 500, message: t(messages.notesTooLong) } }}`
  が設定されており、メッセージ自体は定義されている。保存ボタンの無効化制御
  （`FormSubmitButton` が invalid 判定でボタンをクリック不能にする挙動）と、
  フィールド単位のエラーメッセージ表示のタイミング（onChange 時に即時表示されるか、
  送信試行後にのみ表示されるか等）の組み合わせにより、ユーザーが「なぜ保存できないか」を
  画面上で確認できない可能性がある。
- **判断**: 保存が実際に阻止される点（データ整合性）は満たされているが、
  要件定義書 FR-3(2) の「エラー表示」という受入条件の文言に対しては**未達の疑いがある
  実装上の欠陥候補**として記録する。実装は変更していないため、原因の断定（表示条件の
  詳細なコード修正提案）はここでは行わず、事象の記録に留める。

## 4. スコープ外（US-201 と無関係）の観測事項

以下は notes 機能と直接関係しない既存スイートで観測された失敗であり、参考情報として記録する
（実装・テストともに変更していないため、原因の深掘りはスコープ外とした）。

- `login.spec.ts`: ログイン成功後の遷移先が `/dashboard` ではなく `/websites` になっている
  （テストの期待値と実際の挙動が異なる）。
- `login.spec.ts`: バリデーションエラー時に `Required` テキストが2箇所（ユーザー名・パスワード）に
  表示されるため、`getByText(/Required/i)` が strict mode violation で失敗する。
- `user.spec.ts` / `website.spec.ts`: 上記ログイン遷移先の違いに連動してか、
  後続のページ遷移・要素待機がタイムアウトする。
- `api-user.spec.ts`: 「returns all users when admin access is used」が
  レスポンスに `password` プロパティの存在を期待しているが実際には含まれない
  （セキュリティ的にはパスワードを返さない方が適切であり、この既存テストの期待値自体が
  疑わしい可能性がある）。

## 5. 結論

- US-201 の中核機能（編集画面からのメモ入力・保存・永続化、境界値、null後方互換、
  更新API経由の権限制御・データ正規化）は実装どおりに動作していることを確認した。
- 検出した8件の notes 関連テスト失敗のうち7件は、E2E テストのフィクスチャヘルパー
  （`addWebsite` の `notes` 引数）が API 仕様（作成時は notes 非対応）と整合していない
  ことに起因する**テスト側の不整合**であると切り分けた。実装の修正は不要と考えられるが、
  テスト側の改修（作成後に更新APIでメモを設定するようフィクスチャを直す等）が今後の課題として
  残る。
- 1件（S6: 501文字超入力時のエラー表示）は、保存のブロック自体は機能しているものの、
  ユーザーへの検証エラー表示が確認できず、実装側の欠陥候補として記録した。
- 上記のいずれについても、本フェーズの制約に従い実装・テストコードの修正は行っていない。
