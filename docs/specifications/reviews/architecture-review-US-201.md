# 全体アーキテクチャ設計レビュー結果 US-201: ウェブサイトへのメモ（notes）追加

## 1. レビュー観点

- レイヤ間の依存方向・責務分離が守られているか
- 既存アーキテクチャパターンからの逸脱がないか
- 変更範囲が要件に対して過不足ないか（過剰設計／過小設計の回避）
- 非機能要件（性能・可用性・国際化）への配慮

## 2. 懸念点と対応

### 懸念1: UI 層（一覧・編集画面）とバックエンド層の変更を同一ストーリーで扱うことの妥当性
- **懸念**: 本フェーズはインターフェース設計であり、UI（frontend-engineer領域）とAPI/DB（backend-architect領域）の両方にまたがる設計を1つのアーキテクチャ文書に含めている。責務が混在していないか。
- **対応**: アーキテクチャ設計書ではレイヤごとに変更点をテーブルで明示的に分離し（§2.1）、UI 実装の詳細（省略表示の具体的な文字数・行数等）は frontend-engineer の裁量事項として明確に切り分けた（要件定義書 §7-2 の前提を踏襲）。アーキテクチャ層としては「どのコンポーネントが変更対象か」までを定義し、実装の詳細までは踏み込まない設計とした。
- **結論**: 責務分離は文書構成上担保されており、問題ないと判断。

### 懸念2: 既存の「ウェブサイト」ドメインへの属性追加が、将来的なドメイン肥大化につながらないか
- **懸念**: Website モデルは既に `recorderEnabled`, `replayConfig` など多数の付帯属性を持っており、今後も同様の追加が続くと「なんでもウェブサイトに属性追加する」というアンチパターンに陥るリスクがある。
- **対応**: 本設計では「メモは検索・フィルタ・履歴管理を伴わない単純な属性である」という要件上の制約（対象外スコープ）を根拠に、既存モデルへの属性追加が適切と判断した。今後、検索・履歴・複雑な振る舞いを伴う属性が追加される場合は、都度「単純な属性か、独立した集約とすべきか」を判断する原則を明文化した（data-specification.md §4）。
- **結論**: 今回のスコープでは属性追加が適切。将来の判断基準も設計判断根拠として文書化済みであり、無秩序な肥大化を防ぐガイドラインとして機能する。

### 懸念3: 権限モデルを一切変更しないことによる見落としリスク
- **懸念**: 「新規権限を設けない」という判断が、実は要件が求める微妙な権限区分（例: 閲覧のみ可能なユーザーに対するメモの見え方）を見落としていないか。
- **対応**: 要件の受け入れ条件（US-201-6）を再確認した結果、「閲覧権限があればメモは閲覧できるが、編集はサーバー側の更新権限チェックで拒否される」という設計で全ての受け入れ条件（更新拒否・閲覧可・更新権限保持者の成功）を満たせることを確認した。新規権限区分を設ける必要はない。
- **結論**: 既存権限モデルの流用で要件を満たせると判断し、懸念は解消。

## 3. 検討した代替案と却下理由（再掲・要点）

| 代替案 | 却下理由 |
|---|---|
| メモを独立したドメイン（別テーブル・別サービス）として設計 | 変更履歴・複数メモ等の将来拡張が対象外と明記されており、現時点でのオーバーエンジニアリングになる。 |
| メモ専用の権限区分を新設 | 要件が既存の更新権限チェックへの準拠を明示しており、新設は要件外の複雑化。 |

## 4. 総合評価

US-201 は「既存のウェブサイトドメインへの単純な属性追加」という性質が強く、新規レイヤ・新規サービス・新規権限を導入せず、既存のレイヤ構成（UI → API → 権限 → クエリ → DB）の各層に最小限の変更を加える設計とした。要件の Must 項目（入力・永続化・バリデーション・後方互換性・権限制御）をすべて満たしつつ、YAGNI の原則に従い過剰な抽象化を避けている。将来のドメイン肥大化への懸念に対しては、判断基準を設計文書に明文化することで対処した。
