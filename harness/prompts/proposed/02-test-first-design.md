# フェーズ: E2E/インターフェース/コンポーネントテスト設計＆テストコード作成＆レビュー（提案プロセス）

あなたはテスト設計とインターフェース設計を担当します。**必ず `test-engineer` スキルを使って**作業し、
API・ドメインモデル・データ構造の設計には **`backend-architect` スキル**、UI に関わるインターフェースには
**`frontend-engineer` スキル**の観点も取り入れてください。
対象プロジェクト: **{{PROJECT_NAME}}**（実装は {{SOURCE_IMPL}} 配下）

このフェーズの成果物（設計とテストコード）が**重点レビューの対象**です。
後続の実装フェーズは「ここでレビュー済みのテストを緑にする作業」になります。

## 入力（既存の成果物を読むこと）
- `{{DOCS_REQUIREMENTS}}/requirement-{{STORY}}.md`

## やること（この順序で行う）
1. API・ドメインモデル・データ構造・コンポーネント間インターフェースを設計する。
2. **テスト容易性の契約を確定する**（実装が無い状態でテストを書くために必須）。
   次の項目を設計書に**具体値まで**書き切ること。
   - ルーティング（パス ↔ ページ）
   - テスト用セレクタ規約（`{{CONVENTIONS_TEST_ID_ATTRIBUTE}}` の命名規則と、このストーリーで使う一覧）
   - フォーム項目の識別子
   - 画面に表示するエラーメッセージ文言
   - API のエラーレスポンス形式と HTTP ステータス
   - コンポーネントテストのエントリポイント（ルート単位のページモジュールのパス）

   > **契約に含めないもの: 子コンポーネントの分割方針と props 署名。**
   > 実装前に内部構造まで固定すると、実装フェーズで「設計どおりに分割したらテストが落ちる」が発生し、
   > 「レビュー済みテストは変更しない」という後続フェーズの制約と正面衝突する。
   > 契約は**外から観測できるもの（URL・DOM・HTTP）に限る**こと。
3. 要件を基点に E2E テストの観点・シナリオを設計し、受入条件との対応表（網羅度トレーサビリティ）を作る。
4. コンポーネントテストの観点・シナリオを設計し、受入条件との対応表を作る。
5. **E2E（Playwright）とコンポーネントテスト（Vitest）のテストコードを実際に書く。**
   E2E は `{{SOURCE_E2E_TESTS}}` 配下、コンポーネントテストは {{SOURCE_COMPONENT_TESTS}} 配下に置く。
   **テストランナーが拾える命名規則**（設定ファイルの include / testMatch 等）に必ず従うこと。
6. **テストが「実装がまだ無いために失敗している」ことを確認し、記録する。**
   - `npx playwright test --list` … シナリオが列挙できる＝構文・収集が成立している
   - `npm run test:unit` … 失敗理由が「実装未存在／期待値未達」であることを確認する
   - **この確認を省くと、収集すらされないテストが実装フェーズで「全部緑」に化けて検証が無効になる。**
7. 設計とテストのセルフレビュー結果（懸念点・代替案・却下理由）を残す。

## 出力
### 設計の最終成果物（ストーリーをまたいで蓄積する）
**既存ファイルがあれば修正し、無ければ新規作成する**（ディレクトリが無ければ作成する）。
設計レビューの結果はこれらのファイルには記載しない。
- `{{DOCS_SPECIFICATIONS}}/api-specification.md` … API設計の最終成果物として設計結果とその根拠を記載。
- `{{DOCS_SPECIFICATIONS}}/data-specification.md` … データモデル／データベーススキーマ設計の最終成果物として設計結果とその根拠を記載。
- `{{DOCS_SPECIFICATIONS}}/architecture-specification.md` … 全体アーキテクチャ設計の最終成果物として設計結果とその根拠を記載。
  **手順2の「テスト容易性の契約」はこのファイルに独立した節を設けて記載する。**

### 設計レビュー結果（ストーリーごとに新規作成する）
- `{{DOCS_SPEC_REVIEWS}}/api-specification-review-{{STORY}}.md` … API設計レビュー結果。
- `{{DOCS_SPEC_REVIEWS}}/data-specification-review-{{STORY}}.md` … データモデル／データベーススキーマ設計レビュー結果。
- `{{DOCS_SPEC_REVIEWS}}/architecture-review-{{STORY}}.md` … 全体アーキテクチャ設計レビュー結果。

### テスト設計（ストーリーごとに新規作成する）
- `{{DOCS_E2E}}/e2e-{{STORY}}.md` … E2E の観点・シナリオ・受入条件との対応表
- `{{DOCS_COMPONENT_TESTS}}/component-test-design-{{STORY}}.md` … コンポーネントテストの観点・シナリオ・受入条件との対応表
- `{{DOCS_COMPONENT_TESTS}}/test-readiness-{{STORY}}.md` … 手順6の確認記録。
  実行したコマンド・列挙されたシナリオ数・失敗したテストと**その失敗理由**（実装未存在であること）を記載する。

### テストコード
- `{{SOURCE_E2E_TESTS}}` 配下に Playwright の E2E テスト
- {{SOURCE_COMPONENT_TESTS}} 配下にコンポーネントテスト（ディレクトリが無ければ作成する）

> **コンポーネントテストは必ず {{SOURCE_COMPONENT_TESTS}} 配下に置くこと。**
> このディレクトリは「**このフェーズで作成され、人間のレビューを受けたテスト**」の置き場であり、
> 後続フェーズが書く未レビューのユニットテストとパスで区別できる必要がある。
> 混在すると、実装フェーズのレビュー範囲判定（何がレビュー済みテストで担保されているか）の
> 根拠が失われる。既存のテストランナー設定のまま収集されるので、設定ファイルは変更しないこと。

## 制約（検証の再現性のため厳守）
- `stories/{{STORY}}/acceptance-criteria.md` … このファイルは検証時に使用するものなので**絶対に読み込まないこと**
- **実装本体は書かない**。{{SOURCE_IMPL}} の `src` 配下は変更しない。
  テストを通すためのスタブ・空実装・ダミーの型定義も**作らない**（テストは失敗したままでよい）。
- **ユニットテストはこのフェーズでは書かない**（実装フェーズの担当）。
  したがって {{SOURCE_UNIT_TESTS}} 直下には何も置かない（このフェーズが書くのは
  {{SOURCE_COMPONENT_TESTS}} 配下のコンポーネントテストと `{{SOURCE_E2E_TESTS}}` 配下の E2E だけ）。
- **コンポーネントテストの対象はルート単位のエントリポイント**（`app/**/page.tsx` 等）**に限定する。**
  内部の子コンポーネントをどう分割するかは実装フェーズの裁量に残すこと。
- **コンポーネントテストのアサーションは DOM ベース（role / `{{CONVENTIONS_TEST_ID_ATTRIBUTE}}` / 表示文言）のみとする。**
  props 署名・内部の構造・子コンポーネントの呼ばれ方には依存させない
  （実装フェーズでテストの書き換えが必要になるのを防ぐため）。
- 要件定義・受入条件ファイルは編集しない。
- **既存依存のバージョンは変更しない**（lockfile で固定されている）。テスト用ライブラリの追加は
  必要と判断すれば可。追加した場合は `{{DOCS_COMPONENT_TESTS}}/test-readiness-{{STORY}}.md` に
  **追加したライブラリと採用理由**を記録する。
- テストが失敗する状態でコミットしてよい（メッセージ: `[{{STORY}}] test-first design + tests`）。
