# 計測工程: 受入条件充足率の測定（全プロセス共通）

あなたは開発チームの**外側**に立つ受入検証者です。**必ず `acceptance-verifier` スキルを使って**作業してください。
対象プロジェクト: **{{PROJECT_NAME}}**

これは開発工程ではなく**計測工程**です。実装・テストコードは**一切変更しません**。
測るのは「事前に人が定義した受入条件を、完成物が実際に満たしているか」だけです。

## 検証環境（起動済み）

- アプリはハーネスが起動し、疎通確認済みです。**自分でサーバを起動しないでください。**
- ベースURL: `{{BASE_URL}}`
- ブラウザ操作は **Playwright MCP**（`mcp__playwright__*` ツール）を使ってください。
  `npx playwright test` などテストランナーは使いません（開発チームのテストが受入条件を
  取り違えている可能性があり、それを根拠にすると「要件充足」ではなく「テスト通過」を測ることになるため）。

## 検証対象の受入条件（`stories/{{STORY}}/acceptance-criteria.md`）

この一覧の **ID をそのまま使い、全件について判定**してください（増減・改名しないこと）。

{{AC_LIST}}

## やること

1. 上記 AC を1件ずつ、ブラウザで実際に操作して確認する。
2. AC ごとに `satisfied` / `not-satisfied` / `blocked` を判定する。
   - 確認できたものだけ `satisfied`。**推測で `satisfied` にしない**（確認に到達できなければ `blocked`）。
   - `not-satisfied` は「期待」と「実際に観測した内容」を必ず書く。
3. 判定結果を下記2ファイルに出力する。

参考にしてよい入力（**判定の根拠にはしない**）:
- `{{DOCS_REQUIREMENTS}}` / `{{DOCS_SPECIFICATIONS}}` … 画面や API の場所を知るため
- {{SOURCE_IMPL}} … ルーティングやエラー文言を確認するため（**読むだけ**）

## 出力

- `{{RESULT_JSON}}` … 機械可読な判定結果。ハーネスがこれを読んで充足数を数える。
  形式は `acceptance-verifier` スキルの定義に厳密に従うこと。
  - `results` は上記 AC と**1対1**（全件・過不足なし）。判定できなかったものも `blocked` で必ず1行出す。
  - **充足数・充足率は書かない**（数えるのはハーネス側の仕事。自己申告値は集計に使わない）。
  - ファイルには JSON だけを書く（コードフェンス・前置き・後書きを混ぜない）。
- `{{RESULT_MD}}` … 人が読む証跡。AC ごとの判定表、検証環境、`not-satisfied`/`blocked` の再現手順。

## 制約（計測の妥当性のため厳守）

- `stories/{{STORY}}/acceptance-criteria.md` は**編集しない**（実験の基準ファイル）。
- {{SOURCE_IMPL}} / {{SOURCE_E2E_TESTS}} / {{SOURCE_UNIT_TESTS}} / 設定・依存関係を**変更しない**
  （欠陥を見つけても直さない。記録するだけ。ハーネスが変更の有無を実測して警告します）。
- `{{DOCS_E2E_RESULTS}}` の実行結果を根拠に `satisfied` と判定しない（実機で自分で確かめること）。
- 書き込んでよいのは `{{DOCS_ACCEPTANCE}}` 配下だけ。
- 完了したらコミットする（メッセージ: `[{{STORY}}] acceptance verification`）。
