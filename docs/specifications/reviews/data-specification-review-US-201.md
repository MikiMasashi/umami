# Data Specification Review: US-201

## セルフレビュー結果

### 採用案

`website` テーブルに nullable `notes varchar(500)` を追加する設計を採用した。

根拠:

- メモは Website に 1:1 で紐づく単一属性であり、独立したライフサイクルを持たない。
- 既存一覧・詳細取得で Website と同時に必要になる。
- nullable カラム追加だけで既存レコードの後方互換を保てる。

### 懸念点

| 懸念 | 評価 | 対応 |
| --- | --- | --- |
| 自由記述を Website テーブルに置くことで行サイズが増える | 最大 500 文字で、ページング済み設定一覧の用途に限定される | JOIN 回避と実装単純性を優先。 |
| 将来、履歴・監査が必要になった場合に単一カラムでは不足する | US-201 では履歴・監査は対象外 | 将来要件が出た時点で履歴テーブルを追加する。 |
| `null` と空文字が混在する可能性 | UI 表示条件が不安定になる | 保存時に `null` 正規化するルールを仕様化。 |
| `varchar(500)` の DB 制約と zod 検証の差異 | DB 例外になる前に API で拒否すべき | サーバー側 zod validation を必須にする。 |

### 代替案と却下理由

| 代替案 | 却下理由 |
| --- | --- |
| `website_note` テーブルを作る | 1:1 の単純属性に対して JOIN と repository 分岐が増える。履歴・複数メモ要件がない。 |
| JSON カラムへ設定値として格納する | 型安全性・DB 制約・Prisma 型生成の面で単一カラムより不利。 |
| `text` 型にして API だけで 500 文字制限する | DB レベルの最大長意図が薄れ、不正経路で過大データが入り得る。 |
| `NOT NULL DEFAULT ''` にする | 未設定状態が空文字固定になり、要件の `null` 許容・既存行互換に対して不要な書き換えが発生する。 |
| `notes` にインデックスを張る | 検索・ソート対象外であり、更新コストだけが増える。 |

### 結論

nullable `varchar(500)` カラム追加は、US-201 の保存・後方互換・性能要件に対して最小かつ十分なデータ設計である。検索・履歴などの将来拡張は、要件化された時点で別設計として追加する。
