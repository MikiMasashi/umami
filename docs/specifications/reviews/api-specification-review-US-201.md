# API設計レビュー結果 (US-201)

## 1. レビュー観点

- 既存API（`GET /api/websites`, `GET /api/websites/:websiteId`, `POST /api/websites/:websiteId`）との整合性
- FR-1〜FR-10、AC-1〜AC-10（受入条件そのものは参照禁止のため、要件定義書の機能要件・ユーザーストーリー記載内容のみを根拠とする）の充足
- NFR-1〜NFR-5との整合性

## 2. 懸念点と検討

### 懸念点1: `notes` を `POST /api/websites`（新規作成）に含めないことの是非

- **懸念**: 新規作成時にメモを同時入力したいニーズが将来出る可能性がある。
- **検討**: 要件定義書は「設定編集画面でのメモの入力・編集・保存」（FR-1）のみを対象としており、新規作成フォームへの追加は明記されていない。対象外にスコープを絞ることで変更範囲を最小化する。
- **結論**: 今回は `POST /api/websites`（作成API）へのフィールド追加は行わない。将来ニーズが出た場合は別ストーリーとして追加する。DBスキーマ側は既に `nullable` のため、追加時の後方互換性の問題はない。

### 懸念点2: `notes` を `nullable().optional()` にする必要性

- **代替案A**: `optional()` のみとし、空にしたい場合は空文字列 `''` を送らせる。
- **代替案B（採用）**: `nullable().optional()` とし、`null` で明示的にクリアも可能にする。
- **理由**: `domain` や `shareId` など既存フィールドで `nullable()` パターンが使われている箇所があり（`shareId: z.string().max(50).nullable().optional()`）、命名・型設計の一貫性を優先した。また空文字列とNULLの両方を「メモなし」として扱えるようにすることで、フロントエンドの実装自由度を確保する。
- **却下理由（代替案A）**: 空文字列のみをクリア手段とすると、DB上は空文字列がずっと残り「未設定」と「空文字列」の区別がUI上曖昧になる懸念があったため採用しなかった。ただし実装は空文字列・NULLどちらでも「表示なし」として扱う設計とし（FR-7）、実質的な挙動差は生じない。

### 懸念点3: メモ専用の権限チェックを設けないことの妥当性

- **懸念**: FR-9は「メモの変更」を対象にした権限要件であり、メモ専用のガードが必要ではないか。
- **検討**: 現行の `POST /api/websites/:websiteId` は単一のAPIで `name`/`domain`/`replayConfig` 等をまとめて更新する設計であり、フィールド単位の権限分岐は存在しない。`notes` のみ別の権限にすると既存の設計パターン（1リクエスト＝1権限判定）と矛盾し、実装・テストの複雑性が増す。
- **結論**: `canUpdateWebsite` によるAPI全体の権限チェックをそのまま流用する設計を採用。要件定義書FR-9も「APIレベル・UIレベルの両方でメモの変更を行えない」とあり、既存の更新権限モデルへの準拠で充足可能と判断した。

### 懸念点4: クライアント側バリデーションの実装場所（`rules.maxLength` vs zod共有）

- **代替案A**: `react-hook-form` の `rules.maxLength` をフォーム側に個別定義（採用）。
- **代替案B**: サーバー側のzodスキーマをクライアントと共有し、単一の定義から両方のバリデーションを生成する。
- **検討**: `WebsiteEditForm.tsx` の既存パターン（`domain` フィールドの `pattern` バリデーション）はフォーム側に個別の `rules` を定義するスタイルであり、zodスキーマ共有の仕組みは現状のコードベースに存在しない。
- **却下理由（代替案B）**: 大規模なリファクタリングが必要になり、本ストーリーのスコープ（メモ機能の追加）を超えるため採用しなかった。ただし将来的な共通化の余地はある旨を留意事項として残す。

### 懸念点5: 一覧APIのレスポンスサイズ増加

- **懸念**: 一覧取得時に全ウェブサイト分の `notes`（最大500文字×件数）を毎回返すことによるペイロード増加。
- **検討**: 既存の `domain`（`VARCHAR(500)`）も同様に全件返しているため、アーキテクチャ上の既存パターンと整合する。件数が非常に多い場合の最適化（サーバー側での切り詰め等）は本要件（FR-5〜7は「表示」の要件であり、切り詰めはUI側で行う前提）からは必須ではないと判断。
- **結論**: 現時点では最適化を行わず、必要であれば別途パフォーマンス改善ストーリーとして扱う。

## 3. 却下した代替案のまとめ

| 代替案 | 却下理由 |
|---|---|
| 新規作成APIにも`notes`を追加 | 要件定義書のスコープ外（設定編集画面のみが対象） |
| 空文字列のみでクリア可能とする（`nullable`なし） | 既存フィールド（`shareId`等）の設計パターンと不整合、UI実装の自由度低下 |
| `notes`専用の権限判定関数を新設 | 既存の1リクエスト＝1権限判定モデルと矛盾し複雑化 |
| zodスキーマをクライアント・サーバーで共有 | 既存コードベースに共有基盤がなく、スコープを超える大規模変更になる |
| 一覧APIでnotesを事前に切り詰めて返す | 現要件では必須ではなく、既存の`domain`と同様の全件返却パターンで十分 |

## 4. 実装フェーズへの申し送り事項

- ラベル・エラーメッセージの多言語キー名（`label.notes`, `message.notes-too-long` 等）は実装時に既存の命名規則・翻訳ファイル（`en.json`等）に合わせて最終決定すること。
- 一覧の省略表示の具体的な文字数・ツールチップでの全文表示要否は要件定義書「疑問点」に記載の未確定事項であり、実装フェーズ・関係者確認により最終決定すること。
