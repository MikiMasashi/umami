# データ仕様レビュー結果: US-201（ウェブサイトへのメモ機能）

## レビュー観点と結論

| 観点 | 判定 | コメント |
|---|---|---|
| 既存カラムへの非破壊性 | OK | `ADD COLUMN` のみ。既存カラムの型・NULL制約・デフォルト値は一切変更していない。 |
| NULL許容による後方互換性 | OK | `notes String?` により既存レコードは自動的に `NULL`。FR-5の「既存ウェブサイトが引き続きエラーなく動作する」を満たす。 |
| 文字数上限のDBレベル担保 | OK | `VarChar(500)` により、アプリ層バリデーションをすり抜けた場合でもDBレベルで超過データの保存を防止（ただしPostgreSQLは超過時エラーで弾く形になるため、アプリ層で必ず事前検証する運用が前提。5章参照）。 |
| マイグレーションの命名・配置規則 | OK | 既存の `NN_description` 連番規則（最新 `20_add_heatmap`）に従い `21_add_website_notes` とした。 |

## 懸念点

1. **DBレベルバリデーションのエラー時UX**
   - 懸念: サーバー側zodバリデーション（500文字上限）を回避してDBに直接501文字以上のデータが渡った場合、PostgreSQLの `VarChar(500)` 制約違反で例外が発生し、既存の `updateWebsite()` はこの例外を特別扱いしていない。
   - 対応方針: 通常のAPIフローでは zod が先にブロックするため実運用上は到達しない想定。念のため、API仕様側で zod による事前チェックを「最終防衛ライン」ではなく「唯一の実行経路」として設計し、DB制約はあくまで多層防御の保険と位置づけた（データ仕様書 5章の代替案比較に記載）。追加のtry-catch分岐は本要件のスコープでは過剰と判断し見送った。

2. **空文字とNULLの意味的差異**
   - 懸念: 「メモが空文字で保存される」ケースと「メモキー自体が未指定（更新対象外）」のケースを区別する必要があるか。
   - 検討: 要件（FR-2最後の受け入れ条件）は「メモ欄を空にして保存 → メモ未設定の状態として保存」と明記されており、空文字とNULL未設定を区別する要件はない。そのため空文字は常にNULLへ正規化する方針とした（3章）。

3. **文字数カウント方式の曖昧さ**
   - 懸念: サロゲートペア（絵文字等）を1文字としてカウントすべきか、2としてカウントすべきかで、フロントとDBの上限判定がズレる可能性がある。
   - 対応方針: 要件定義書 8章-2 にて「umami の他のテキスト項目と同様の一般的な文字数カウント方式」との方針が確認済みであるため、`String.prototype.length`（UTF-16コード単位、既存 `name`/`domain` 相当の単純な方式）で統一し、フロント・サーバーで同一基準を用いることでズレを防止する。

## 却下した代替案（データ仕様書に記載済みのものの要約と選定理由）

- 別テーブル `WebsiteNote` 化 → 過剰設計のため却下（YAGNI）。
- `Json` 型汎用フィールド化 → 型安全性・DB制約の喪失のため却下。
- `TEXT`（無制限）+ アプリ層のみ制御 → 多層防御の観点から却下、`VarChar(500)` を採用。

## 総合判定

**承認**。既存のWebsiteモデルへの非破壊的な属性追加として、要件（FR-1, FR-5, 非機能要件「互換性」「入力検証」）を満たす設計であることを確認した。実装フェーズへ引き継ぐ。
