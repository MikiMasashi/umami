# E2E テスト設計書 US-201: ウェブサイトへのメモ（notes）機能

このドキュメントは `docs/requirements/requirement-US-201.md`（要件定義書）、
`docs/specifications/api-specification.md`（API仕様書）、
`docs/implementation/implementation-notes-US-201.md`（実装メモ）を基に、
US-201 の E2E テスト観点・シナリオ・受入条件トレーサビリティを整理したものである。

> 補足: 検証用の `stories/US-201/acceptance-criteria.md` は本設計の入力として参照していない
> （要件定義書 §4 FR-2〜FR-6 に記載された受入条件のみを基点とした）。

## 1. テスト戦略・スコープ

- テストピラミッドに従い、E2E は「編集画面での保存・永続化」「一覧表示」「権限制御」という
  クリティカルユーザージャーニーに絞る。文字数カウント方式の詳細判定や UI コンポーネントの
  内部実装（`truncateString` の細かいロジック等）は既存の Vitest ユニットテスト
  （`src/tests/...`）で担保されている前提とし、E2E では「ユーザーから見える結果」のみを検証する。
- ブラウザ操作が必須のシナリオ（フォーム入力・保存・リロード・一覧表示）は
  `tests/e2e/website-notes.spec.ts` に、API 契約・権限・境界値など「UIの皮を被らなくても
  自動化価値が高い」シナリオは `tests/e2e/api-website-notes.spec.ts`（Playwright の
  `request` フィクスチャ、`tests/e2e/api-website.spec.ts` と同じスタイル）に分離した。
- 既存の `tests/e2e/helpers.ts` / `tests/e2e/fixtures.ts` を拡張し、新規ヘルパー
  （`addTeamUser` 等）・新規フィクスチャ（`notes`）を追加した。既存テスト
  （`website.spec.ts` 等）の呼び出し互換性は維持している（`addWebsite`/`addUser`/`addTeam`
  の戻り値をレスポンス JSON に変更したが、既存呼び出し側は戻り値を使用していないため
  非破壊）。

## 5. 未カバー・既知の制約（セルフレビューで判明した事項）

- **FR-6 (1) のうち「編集UIから保存を試みる」経路**: 実装メモ §「権限制御（FR-6）について」に
  よれば、メモ欄専用の無効化分岐は追加されておらず、既存の `WebsiteEditForm` 呼び出し元の
  権限ガードにそのまま乗る設計とされている。しかし、その呼び出し元ガードの具体的な実装
  （フォーム全体を読み取り専用にする仕組み）はコードベース内で明確に特定できなかったため、
  UI操作でのブロック確認は本設計では自動化していない。API直接呼び出しでの拒否（V14/S16）と
  読み取り許可（V15/S17）は確実にカバーしているため、受入条件の実質（「書き換えられない」
  「読み取りは可」）は担保できるが、UI上のボタン無効化等の見た目の確認は手動テスト／
  今後の追加課題とする。
- **FR-3 の文字数カウント方式**: 要件定義書 §8-2 のとおり JavaScript の `.length` 基準に
  準拠する前提とし、境界値テスト（500/501文字）は ASCII 文字（`'A'.repeat(n)`）で構成した。
  サロゲートペア・絵文字混在時の厳密な挙動は本 E2E のスコープ外（要件定義書でも
  「詳細は実装時の既存パターンに合わせる」とされ未確定のため）。
- **省略表示の閾値（60文字）**: `WebsitesTable.tsx` の `NOTES_DISPLAY_MAX_LENGTH = 60` は
  実装判断（要件定義書 §8-3 で明記の通り実装時に委ねられた事項）であり、テスト
  （S7）では実装済みの閾値を超える120文字のメモで「省略記号が付く」「元の全文がそのまま
  表示されない」ことのみを確認し、閾値そのもの（60という数値）を固定的に検証する
  ハードコードは避けた（実装側の将来的な調整に対して過度に脆いテストにしないため）。
- **セキュリティ（XSS）**: 非機能要件に XSS 対策への言及があるが、React の標準レンダリング
  （`dangerouslySetInnerHTML` 不使用）に依存した対策であり、実装メモでも既存のユニットテストで
  担保する方針が示されていないため、本 E2E でも `<script>` 注入等の専用シナリオは追加して
  いない。既存の全社的なセキュリティレビュー・単体テストの対象とすることを推奨する。

## 6. 追加ライブラリ

**追加なし。** 既存の `@playwright/test`（package.json 記載のバージョンのまま）のみを使用した。
権限テストで使用した `team-view-only` ロール・チーム作成/ユーザー追加APIは、既存の
`tests/e2e/api-team.spec.ts` ／ `tests/e2e/api-user.spec.ts` で使われているパターンをそのまま
踏襲し、`tests/e2e/helpers.ts` に `addTeamUser` ヘルパーを追加しただけである。

## 7. セルフレビュー

- **設計の一貫性**: 既存の `tests/e2e/*.spec.ts` の記法（`getByTestId`、`authHeaders`、
  `test.describe.configure({ mode: 'serial' })` 等）に合わせてスタイルを統一した。
- **フレーキー対策**: 明示的な `sleep` は使用せず、Playwright の web-first assertion
  （`toBeVisible` / `toHaveValue` / `toContainText` 等の自動待機）のみを利用した。各テストは
  `addWebsite`/`addUser`/`addTeam` で専用データを都度作成し、`afterAll`/テスト末尾で
  削除することで、並列実行・他テストとの独立性を確保している。
- **セレクタ方針**: 既存実装が付与している `data-test` 属性（`getByTestId`）を優先して使用し、
  CSS/XPath への依存を避けた。一覧の列判定のみ、既存テスト（`website.spec.ts`）にならって
  `td[label="..."]` を使用している（DataTable コンポーネントが `label` 属性を td に付与する
  既存の慣例に合わせたもの）。
- **静的検証**: `npx biome check`（対象ファイルへの `--write` 適用後）でエラーなしを確認。
  `npx tsc --noEmit` はリポジトリ環境固有の既存エラー（`@/generated/prisma/client` が
  ローカル未生成のため発生する、本タスク変更前から存在するエラー）のみで、新規追加した
  E2E テストファイルに起因する型エラーはないことを確認した。`npx playwright test --list`
  で全18件のテストが正しく認識されることを確認済み（実行には DB/Prisma クライアント生成等の
  環境準備が必要なため、既存の `tests/e2e/*.spec.ts` と同様、実際のブラウザ実行は
  CI/開発環境側のセットアップに委ねる）。
- **見つかった課題**: 上記「5. 未カバー・既知の制約」に記載の通り、UI上の権限ガード
  （編集ボタン無効化等）の具体実装が特定できなかった点は今後の確認事項として残した。
