# データモデル / DBスキーマ設計レビュー結果: US-201

対象: `docs/specifications/data-specification.md`（US-201 部分）
レビュアー: backend-architect
判定: **承認（実装可）**。以下の懸念・代替案・却下理由を記録する。

---

## 1. 懸念点と対応

### C-1: `VarChar(500)` と zod `max(500)` の単位不一致（中）
- **懸念**: 要件の上限は「JS `String.length` で500」（Q1）。一方 PostgreSQL の `VARCHAR(n)` は「n 文字（コードポイント数に近い）」で数える。サロゲートペア（絵文字等）や結合文字を含む場合、`String.length`（UTF-16 コード単位）と DB のカウントがずれ、zod は通過するが DB でエラー、あるいはその逆が起こりうる。
- **決定**: **正準の上限判定はサーバ zod（`String.length` 準拠）**とし、DB `VarChar(500)` は防御的制約（保険）として残す。両者ずれによる稀な DB エラーは `serverError` で捕捉可能。厳密一致が問題化した場合は DB 側を `@db.VarChar(1000)` へ緩めるか `Text` 化する余地を残す（下記代替案）。
- **代償**: 稀な入力で DB 制約が先に発火する可能性。実運用上 500 文字メモで絵文字が上限ちょうどに来るケースは極めて低頻度と判断し許容。

### C-2: `Text` 型にしない判断（低）
- **懸念**: 可変長上限を DB で厳密に持たせるより `Text`（無制限）にして上限はアプリのみで持つ設計もある。
- **決定**: 既存 `domain String? @db.VarChar(500)` と様式を揃え **`VarChar(500)` を採用**。多層防御になり、既存パターンとの一貫性・可読性を優先。

### C-3: `@map` の要否（低）
- **決定**: フィールド名 `notes` は物理名と一致し衝突しないため `@map` 不要。`name`/`domain` と同じ扱い。camelCase フィールド（`recorderEnabled` 等）のみ `@map` を付与する既存規約に整合。

### C-4: 既存データへの影響（高 → 解消）
- nullable カラム追加のみで、既存行は `NULL`。バックフィル不要・デフォルト不要のためオンラインで安全に適用可能（AC-5.1/5.2）。**懸念なし**。

## 2. 代替案と却下理由

| 代替案 | 内容 | 却下理由 |
| --- | --- | --- |
| 別テーブル `website_note` を新設 | 1:1 の子テーブルに分離 | JOIN 追加で一覧が N+1/追加ラウンドトリップになりやすく、非機能パフォーマンス要件に反する。単一フィールドで十分（要件2.2）。削除時の連鎖も自前管理が必要。**却下**。 |
| `Text` 型 + アプリ上限のみ | DB 無制限 | 多層防御が弱まり、既存 `VarChar` 様式とも不一致。**却下**。 |
| `notes` を non-null + default `''` | 空文字既定 | 「未設定」を `null` と `''` で二重表現し AC-3.3/5.3 の判定が複雑化。後方互換の観点でも nullable が自然。**却下**。 |
| `notes` に index / 全文検索 | 検索用索引 | 検索・フィルタは Won't。索引は書き込みコストを増やすだけで無価値。**却下**。 |

---

## 3. 残リスク / フォローアップ
- C-1 の単位不一致は「zod=正準／DB=保険」で運用。契約テストで `String.length` 基準の 500/501 境界を担保する。
- 将来「複数メモ」「履歴」要件が来た場合は、本カラムを残しつつ別コレクションテーブルを新設する拡張とし、既存 `notes` の破壊的変更は避ける。
