# データモデル / DB スキーマ 設計レビュー結果: US-201

- 対象: `docs/specifications/data-specification.md` §2（`Website.notes`）
- レビュー観点: 後方互換 / マイグレーション安全性 / 整合性 / パフォーマンス

---

## 1. 良い点

- `notes String? @db.VarChar(500)` は NULL 許容の単純な列追加で、既存行を書き換えず
  ロックも最小のため、ダウンタイムなしで適用可能（NFR-3, AC-8）。
- 検索・並び替え対象外のためインデックスを付けない判断は、要件スコープと NFR-4 に合致。
- 正規化（トリム後空→NULL）を API 層に集約し、DB には「非空文字列 or NULL」のみを
  入れる方針は、一覧の「メモ有無」判定を単純化する。

## 2. 指摘・懸念と対応

| # | 懸念 | 対応 / 判断 |
| --- | --- | --- |
| D-1 | `VARCHAR(500)`（文字数）と zod `.max(500)`（コードポイント）の数え方差異 | 実運用上ほぼ一致。厳密境界（絵文字等）はアプリ側 zod を正とし、DB は上限ガードとして機能。二重防御で問題なし |
| D-2 | 500 バイトではなく 500 文字か | PostgreSQL の `VARCHAR(n)` は n 文字（バイトではない）。OQ-1 の「文字数」と一致 |
| D-3 | 既存 `updateWebsite` が汎用 `data` を受けるため型追加のみで対応可能か | `Prisma.WebsiteUpdateInput` に `notes` が生成されるため、クエリ層の変更は不要（列追加＋`prisma generate`） |

## 3. 代替案と却下理由

- **代替1: `TEXT` 型（無制限）で保存し上限はアプリのみで担保。**
  却下理由: データ肥大化ガードを DB でも持ちたい（FR-3 の意図）。500 文字固定のため
  `VARCHAR(500)` が意図を明示できる。
- **代替2: 別テーブル `website_note` に 1:1 で切り出す。**
  却下理由: 1 サイト 1 メモ・履歴なし（スコープ 4.2）。JOIN と N+1 を招き NFR-4 に不利。
  将来「履歴」を持つ要求が出た時点で再検討する。

## 4. 結論

スキーマ設計を承認。マイグレーションは追加列（NULL デフォルト）のみとし、既存データ
移行スクリプトは不要。
