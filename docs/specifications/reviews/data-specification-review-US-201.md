# データモデル／データベーススキーマ設計レビュー結果 US-201: ウェブサイトへのメモ（notes）追加

## 1. レビュー観点

- 後方互換性（既存レコードへの影響、マイグレーション安全性）
- データ整合性（型・制約の妥当性）
- 将来の拡張性とのバランス（過剰設計を避けつつ拡張の芽を潰していないか）
- 性能・運用面への影響

## 2. 懸念点と対応

### 懸念1: `VarChar(500)` という DB 制約とアプリケーション側バリデーション（500文字）の文字数カウント方式の齟齬
- **懸念**: PostgreSQL の `VARCHAR(n)` は「文字数（Unicode コードポイント単位が基本、実際は文字単位）」で制限するのに対し、JavaScript の `zod` の `.max(500)` は文字列の `.length`（UTF-16 コードユニット数）で判定する。サロゲートペア（絵文字等）を含む文字列では、DB 側の制約とアプリ側の制約がわずかに異なる基準になり得る。
- **対応**: 要件（§7-5）で「特別な文字種制限は設けない」とされており、絵文字を含む極端なケースでの数文字レベルの誤差は許容範囲と判断。DB 制約はあくまで「アプリ側バリデーションをすり抜けた場合の最終防衛線」という位置づけであり、両者が完全に一致しなくても実用上問題はない（data-specification.md §2.1, §4 に明記）。
- **結論**: リスクは低いと判断し許容。将来的に絵文字を含む文字数カウントの厳密化が必要になれば、別途要件化して対応する。

### 懸念2: マイグレーションの命名・連番管理
- **懸念**: 既存マイグレーションは `01_init` 〜 `20_add_heatmap` まで連番管理されており、複数ストーリーが並行して同じ「次の番号」を予約しようとすると衝突する可能性がある。
- **対応**: 本設計では `21_add_website_notes` を提案しているが、実装フェーズで他の未マージ変更と衝突しないか確認する運用上の注意点として記載する（設計文書の記述はあくまで提案であり、実装時に最新の番号を確認する前提）。
- **結論**: 設計上のリスクではなく実装時の運用手順の話であり、致命的な問題ではない。

### 懸念3: 別テーブル化しないことによる将来の変更履歴機能追加時のマイグレーションコスト
- **懸念**: 要件は変更履歴を対象外としているが、将来的に履歴機能が追加された場合、単一カラムから別テーブルへの移行（データ移行を伴う）が必要になる。
- **対応**: 検討の結果、履歴機能が要求されるタイミングで `WebsiteNoteHistory` のような別テーブルを新設し、現行の `notes` カラムを「最新値のキャッシュ」として残す設計へ移行するのが自然であり、現時点で先回りして正規化する必要はないと判断（YAGNI原則の適用）。
- **結論**: 現行スコープでは正規化コストが将来の不確実な要件のためのコストを上回るため、単一カラム追加のままとする判断を維持する。

## 3. 検討した代替案と却下理由（再掲・要点）

| 代替案 | 却下理由 |
|---|---|
| `Text`型＋アプリ層のみのバリデーション | DB制約による多重防御が失われるため不採用。 |
| JSON カラムでのラップ格納 | 構造化データではなく単一のプレーンテキストのため、JSON化のメリットがない。 |
| 物理名を `memo` にする | 要件定義書の論理名（notes）とAPIレスポンスのフィールド名を一致させ、トレーサビリティを優先。 |

## 4. 総合評価

追加カラムは nullable かつデフォルト値なしで既存データへの影響が最小限であり、マイグレーションもシンプルな `ALTER TABLE ADD COLUMN` に留まる。文字数カウント方式の微差は要件の許容範囲内であり、正規化を見送る判断も YAGNI の観点から妥当。US-201 のデータ整合性・後方互換性要件を満たす設計と判断する。
