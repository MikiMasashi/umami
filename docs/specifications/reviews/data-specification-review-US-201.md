# Data Specification Review - US-201

## Review result
- Status: Approved with test strategy alignment

## Reviewed items
- `Website.notes` の型
- NULL 許容
- migration 互換性
- 一覧取得への影響
- テスト層での検証方法

## Decisions
1. `notes String? @db.VarChar(500)` を追加
2. 空文字は DB 保存時に `NULL` 正規化
3. 既存レコード backfill は不要
4. index は追加しない
5. NULL 値はコンポーネント・E2E で「メモなし」として扱う

## Review comments
- 500 文字上限が要件で固定されているため DB 制約で守る設計は妥当
- 単純属性のため別テーブル化しない判断は適切
- 既存レコードを NULL のまま扱えるため安全に migrate できる

## セルフレビュー（テストエンジニア視点）

### ✅ テスト観点での承認事項

1. **NULL 許容による後方互換性**
   - 既存メモなしサイト（notes = NULL）でもエラー不発生 ✅
   - コンポーネント・E2E の「既存サイト表示」シナリオでこれを検証可能

2. **500文字の DB 制約の有効性**
   - DB 層で制約 → アプリケーション層でも同じ検証（Zod）を重複
   - 二重検証により不正入力を確実に防止 ✅
   - テスト観点: コンポーネントテストで 500/501 文字境界をテスト

3. **一覧取得への影響（パフォーマンス）**
   - 非機能要件 3.4「notes フィールド追加で一覧クエリパフォーマンス低下しない」
   - VARCHAR(500) 追加による行サイズ増は許容範囲
   - 次フェーズで column selection 最適化で対応可 ✅

### 代替案検討（却下）

| 案 | 理由 | 判定 |
|---|---|---|
| TEXT 型を採用（サイズ無制限） | 要件 500文字上限違反 | 🚫 却下 |
| 別テーブル `WebsiteNotes` 分離 | 1:1 関係で正規化過度、クエリ複雑化 | 🚫 却下 |
| notes の index 作成 | スコープ外（パフォーマンス要件は次フェーズ） | 🚫 却下 |
| 既存レコード backfill （デフォルト値） | NULL のまま扱うで十分（後方互換性） | ✅ 不要 |

## 最終判定

**✅ 承認** - データ設計はテストで十分検証可能、実装フェーズ移行可
