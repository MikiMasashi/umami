# E2E Test Design US-201

## Scope

E2E tests cover the critical user journeys and API guardrails for website notes. They use role/text selectors where possible and the reviewed `data-test` contract where the UI needs stable form/list hooks.

## Scenarios

| ID | Scenario | Assertions |
| --- | --- | --- |
| E2E-US-201-01 | Save a note <= 500 characters from the website edit page and reload. | `input-notes` is visible, save succeeds, textarea keeps the saved value after reload. |
| E2E-US-201-02 | Show list summaries only for noted websites. | API update returns `notes`; `/settings/websites` renders `website-note-summary-{websiteId}` for noted site and no summary/placeholder for unset site. |
| E2E-US-201-03 | Reject 501-character notes in UI and direct API. | UI shows `Notes must be 500 characters or fewer.`; API returns HTTP 400 with the exact validation error; existing note remains unchanged. |
| E2E-US-201-04 | Clear notes and block unauthorized direct updates. | Blank notes persist as `null`; direct update by a user without update permission returns HTTP 401 and cannot overwrite notes. |

## Review notes

The E2E layer intentionally does not test every rendering detail. It verifies persistence, reload behavior, list visibility, validation, and authorization because those are the cross-layer risks.
